## 已确认结论与证据

### 1. 活动核心模拟与 AI 执行图

- 活动阶段唯一配置为 `src/mods/mod-engine/helpers/mvp-stages-config.default.json` 的 `p8`，共启用 13 个外部业务成员和 9 个引擎成员；源码存在但未列入该配置的系统不属于当前活动回合。
- 核心回合中央登记为 `narrative-round`，owner、failureTarget 与 department 均归 `mod-engine`，subsystem 为 `orchestrator-system`。证据：`src/core/execution/execution-flow-registry.ts`。
- 正式回合 AI 执行图为一次 `ai-narration` 主叙事调用，随后 `ai-data-analysis`、`ai-system-analysis`、`ai-event-recognition`、`ai-plot-guidance`、`ai-talent-growth`、`ai-memory-compression` 六路以同一 `narrative-specialists` 并行组各调用一次。证据：`src/mods/mod-engine/campaigns/default/index.ts`。
- 六路专项使用各自独立冻结输入与结果槽；任一路生成、协议校验、所属合同预检或提交失败都会使本轮进入失败路径，不存在自动重试、格式修复、模型回落或本地内容兜底。
- 下一轮预生成只调用一次主叙事，不执行六路专项、不写正式 Store、时间、存档、诊断或业务状态；正式回合只有在完整 Prompt、消息和请求参数指纹一致时才消费内存候选，否则丢弃并正常发起正式主叙事。证据：`src/mods/mod-engine/helpers/main-narrative-call.ts`、`narrative-pre-generation.ts`、`docs/authority/core-simulation.md`。

### 2. 当前轮正文展示时序

- `ai-narration` 返回并通过严格协议后，`prepare-narrative` 只冻结正文候选，并向 `pendingNarrative` 写入执行编号、回合序号、状态和状态码；该投影不包含正文。
- 页面可据 `pendingNarrative` 显示“故事已返回，正在完成本轮”，但阅读区仍只消费正式 `narrativeHistory`；因此玩家此时看不到新正文。
- `commit-round` 等待六路专项全部成功，按确定顺序提交各所属事务，最后才由 `commitNarrativeResponse()` 把正文加入 `narrativeHistory` 并发布模拟快照。故当前实现没有通过“正文一到即显示、后调用后台完成”缩短当前轮可见等待时间。
- 证据：`src/mods/mod-engine/campaigns/default/index.ts`、`src/mods/mod-engine/subsystems/orchestrator-system/narrative-acceptance-runtime.ts`、`src/mods/mod-pages/pages/game-story/page.tsx`、`docs/authority/core-simulation.md`、`docs/authority/logic-tree.md`。

### 3. Provider、模型、调用参数与失败路径

- 当前逻辑 Provider ID 唯一允许值为 `custom`，含义是玩家自有 API 配置；受保护 Prompt 的服务端目标只允许登记的 DeepSeek 官方 HTTPS 地址。默认预填端点为 `https://api.deepseek.com/v1`，默认模型为 `deepseek-v4-flash`，玩家非空自定义模型覆盖默认值。证据：`src/core/ai-service/provider-config.ts`、`src/core/ai-service/server-provider-targets.ts`、`src/core/ai-service/ai-client/request-body.ts`、`src/mods/mod-settings/store.ts`。
- 主叙事和六路专项共用当前玩家 API Key、Base URL 与模型，没有按调用分配不同模型。六路专项固定 `temperature: 0`、`reasoningEffort: 'disabled'` 并使用非流式调用；主叙事使用设置温度与推理强度，但 `hooks.ts` 固定 `stream: false`，设置中的 `streamingMode` 不进入本调用；设置中的 `topP` 当前也没有接入主叙事请求。故事种子进入主叙事指纹和客户端请求体，但代理对模型名包含 `deepseek` 的目标删除 `seed`，因此默认 DeepSeek 上游不接收该参数。证据：`src/mods/mod-engine/hooks.ts`、`src/mods/mod-engine/helpers/main-narrative-call.ts`、`src/mods/mod-engine/campaigns/default/index.ts`、`src/core/ai-service/ai-client/request-body.ts`、`src/app/api/proxy/route.ts`。
- 代理实际候选数组为 `const modelCandidates = [body.model]`，每次客户端调用最多发起一次上游 `fetch`；连接失败、总时限、上游非成功状态均直接返回失败，不会重试、改换模型或本地修复。`src/app/api/proxy/route.ts:533` 关于“安全切换备用模型”的注释与实时实现不符，是旧机制残留注释，不代表活动能力。
- `upstreamAttempts` 和 `selectedAttempt` 当前只用于单次上游尝试的观测与归档；在现实现中成功或上游 HTTP 失败均为一次记录，连接错误也在第一次失败后立即跳出。

### 4. 调用 ID 与缓存隔离

- 七个逻辑调用 `narrative-main`、`narrative-data-analysis`、`narrative-system-analysis`、`narrative-event-recognition`、`narrative-plot-guidance`、`narrative-talent-growth`、`narrative-memory-compression` 分别映射到七个独立 `InternalCachePool`。证据：`src/core/ai-service/cache-pool.ts`。
- DeepSeek 请求的 `user_id` 由 `als_${cache_pool}_${sha256(normalizedTrustedUserId|cache_pool).slice(0,40)}` 组成。可信主体依次取账号 ID、设备来源 ID、诊断编号、来源 ID；因此同主体同池稳定，跨调用池必然隔离，且不会直接暴露原始主体标识。证据：`src/app/api/proxy/route.ts`。
- 客户端 `sessionId` 不参与代理上游身份组装；缓存隔离依赖 `cache_pool + user_id`。这意味着同一可信主体跨浏览器会话仍复用所属逻辑池，符合稳定缓存池目标，但不提供会话级隔离。
- 主叙事正式调用和下一轮预生成均使用 `narrative-main` 池及相同主体 `user_id`，仅以 `executionKind` 区分观测语义；该设计允许两者命中同一稳定前缀缓存，候选消费安全性另由完整请求指纹保证。
- DeepSeek 身份分支当前由“模型名是否包含 `deepseek`”判断，而不是由已登记 DeepSeek Base URL 判断。默认模型满足条件；若玩家在官方 DeepSeek 地址上填写不含该字符串的模型别名，请求会改发通用 `user` 而非池化 `user_id`，缓存池隔离在该边界退化。

### 6. 天赋位置、稳定前缀与引导区格式

- 主叙事的玩家天赋没有放在 `本轮引导`，而是放在第一条 user 消息 `⟦全局信息⟧` 的 `命格天赋` 字段。该字段把已装备轮回天赋与普通命格合并为一个字符串：轮回天赋使用 `【轮回天赋】名称（说明）：效果`，普通命格使用 `【普通命格】名称：效果；特质说明：说明`。证据：`prompt-talent-projection.ts`、`prompt-context-runtime.ts`、`prompt-builder.ts`。
- `全局信息` 固定键序为：世界设定、世界规则、模组世界规则、世界标签、世界校准、力量体系、命格天赋、角色档案、叙事风格、叙事基调。该段位于记忆和本轮引导之前，整体方向符合慢变内容在前。
- 普通命格会在天赋成长提交后升级名称、说明、效果和版本；下一轮 `命格天赋` 文本随之改变。DeepSeek KV 前缀只能复用到首个不同 Token 之前，因此系统固定 Prompt 与 `命格天赋` 之前的全局字段仍可能命中，从该字段开始的全局后缀、记忆消息和本轮引导都会失去连续前缀命中。当前设计没有实现“把可升级天赋放到后段，避免升级破坏主稳定前缀”的目标。
- 轮回天赋通常跨本局稳定，普通命格可在局内成长；两类内容合并在同一字段，使可变普通命格拖动稳定轮回天赋共同重发。若后续实施优化，应由用户另行确认后拆分稳定轮回天赋与可升级普通命格的装配位置，本次只记录结论。
- `本轮引导` 的实际外层格式是 `⟦本轮引导⟧` 加紧凑 JSON；固定键序为：`当前时间`、`角色现状`、`当前状态`、`最近变化`、`当前情节阶段`、`本轮可回收伏笔`、`本轮触发事项`、`时间跨度摘要`、`已触发因果`、`系统引导`、`本轮玩家行动`、`字数要求`，空值按当前开关省略。
- `系统引导` 是字符串数组，来源固定顺序为：回合系统提示（强制分支/阶段跨越/运气/首轮开场）→ 时间尺度与历法社会作息 → 叙事一致性与条件输出合同。该顺序由来源 `order=10/20/30` 决定，不按文本实际权重重排；高优先级的叙事一致性与输出条件反而位于辅助运气和时间说明之后，不符合“核心原则在前、次要和辅助在后”。
- 固定 system Prompt、全局、记忆、本轮引导的消息级顺序稳定；专项调用也都把服务端固定 system 放在动态 user 消息之前。缓存友好点成立，但主叙事缓存统计中的 `stablePrefixChars` 只记录全局 user 段长度，没有把服务端固定 system Prompt 计入该本地指标，不能单凭该数值还原 Provider 的完整可缓存前缀。

### 7. Prompt 冗余、语义风险与权威漂移

- 强制分支同时由固定 Prompt 的分支政策/输出协议、`mandatory-round-hints` 的“本轮需要出现一个命运分支”和动态输出合同的“本轮请求命运分支”表达；虽然高优先级裁决可消解结果冲突，但同一条件被发送三次。
- 首轮同时发送通用/出生开场指令与动态输出合同的“这是人生首轮”说明；年度时间档在 0 岁时又自带出生开场规则，出生首轮最多出现三处近义指导。
- 时间指导同时包含“当前时间是结束节点”、真实历法窗口、推进天数、档位视角及 `当前时间` 独立字段；真实窗口信息必要，但结束节点与跨度职责在多个字符串中重复。
- `叙事一致性` 动态段再次解释力量体系和当前状态来源，而全局区已经有独立 `力量体系`、`世界设定`、`命格天赋` 与 `当前状态` 字段；启用力量体系时存在可压缩的复述。
- 动态编译器只删除完全相同的整段文本；主叙事组件审计只发现重复 ID、重复标题、全文相同与一个句子被另一句包含，无法识别近义重复、条件覆盖、权重倒置或语义矛盾。

## 最终判断

1. 核心回合当前是“1 次非流式主叙事 + 6 次并行专项 + 统一提交”，不存在正式回合 AI 前调用；预生成是上一轮成功后的可选异步主叙事候选，不是当前回合前置 AI。
2. 正文收到后不会立即进入阅读区；玩家会看到“故事已返回，正在完成本轮”，并继续等待六路最慢专项及提交完成。当前机制没有用先展示正文缩短可见等待。
3. 七路逻辑池在默认 DeepSeek 模型下具备同主体同池稳定、跨池隔离；正式/预生成主叙事共享主池。隔离判断依赖模型名包含 `deepseek`，自定义别名是明确边界。
4. 固定 system 在前、主叙事慢变全局段在记忆和本轮段之前，消息级缓存排序成立；但可升级普通命格位于全局稳定段中部，升级会破坏其后的 KV 前缀，未达到用户期望的天赋升级缓存隔离。
5. 七路 Prompt 均无实战正文示例，但严格正向引导、单行职责单一、显式权重前缀和语义级冲突治理均未完全达标；当前机械门禁标准低于本次用户标准。
6. 引导区格式固定、键序确定，但高权重内容没有排在系统引导数组最前，且分支、首轮、时间和力量一致性存在可精简重复。
7. Skill 入口与 references 均不大，路由总体有效；8 份被审 Skill 同样不符合全正向和显式权重前缀标准，并有跨层重复。历史聚合文档和少数实时源才是主要体积风险。
8. 活动权威存在多处与实时调用、输入和等待机制不一致的内容；后续任何整改都应单独说明修改范围、Prompt/缓存/等待行为与验证，再取得用户确认。本次没有实施整改。
