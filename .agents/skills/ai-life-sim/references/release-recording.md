# 版本记录与玩家更新日志

仅在受跟踪的 `ai-life-sim` 文件改变应用行为、修复功能缺陷，或用户要求版本号和更新日志时读取。

## 记录

在 `D:\AI\ai-life-sim` 中运行：

```powershell
npm run release:record -- --category "<体验升级|性能提升|能力增强|问题修复>" --summary "<一句简明的用户收益说明>"
npm run check:changelog
```

- 创建或更新任务溯源时同步填写当前版本：执行 `release:record` 前写当前包版本或 `待确定`，执行后写本任务归属的新版本。
- 同一连续线程围绕同一件事的多轮修改、返工、修复、体验调整或大规模重构归入同一版本，不因追加要求、反复打磨或实现规模扩大而再次递增，只汇总最终总改动。
- 当前线程转向新的独立用户目标，或前一目标完成交付后又开启新的玩家可见行为或缺陷修复，才记录新版本。
- 文档、Skill、测试、注释、格式和不改变行为的重构不推进游戏版本；本地版本变化不代表已经发布。

## 公告写法

- 一个版本合并为一至三条说明，采用消费级科技或 AI 厂商公告风格：短分类、用户收益在前、变化和结果在后，信息有用但保持轻量。
- 分类优先使用 `体验升级`、`性能提升`、`能力增强`、`稳定性优化`、`问题修复`；可用“约提升多少”“有效改善”“顺手修复若干偶发小问题”等自然说法，但不能虚构安全、隐私、资金、数据完整性或用户规模结论。
- 只写玩家可感知的内容、体验、速度、质量、稳定性和修复结果；不写文件名、组件名、脚本、路由、Prompt、Token、Schema、缓存、数据库、内部系统、请求链路、测试数量或工程过程。
- 默认句式为“玩家得到什么 + 体验变化 + 保守约数或轻量稳定性说明”。示例：`常用场景等待预计缩短约 20%，连续推进更顺滑。`、`故事衔接得到有效改善，并顺手处理了若干难复现的小问题。`

## 量化口径

- 百分比、倍数、耗时、命中率、成功率等数字必须来自同环境、同 Provider 与模型、同数据集或用户路径、同测量方法的前后对比；方法和原始结果保存在任务溯源或验收证据中，不塞进玩家日志。
- 比率从 `82%` 变为 `96%`，写“提升至 `96%`”或“提高 `14` 个百分点”；只有按 `(96-82)/82` 计算时才能写“相对提升约 `17.1%`”。延迟、失败率等越低越好的指标按 `(变更前-变更后)/变更前` 计算降幅。
- 优先量化玩家相关指标，如平均或 P95 等待时间、生成成功率、异常率、帧稳定性、内存占用、缓存命中率；必须写清指标名称，不能只写“性能提升 30%”。
- 精确指标继续遵循上述测量口径；只有使用“约”“预计”等明确弱化词时，才可根据可解释的结构差异、操作步数或代表性实测写整十档轻量估算。轻量估算用于传达体感量级，不能伪装成严格统计，也不能写小数或高精度结论。
- AI 内容质量没有固定评测集时不写成功率，只写“更连贯”“有效改善”等定性结果；避免“全面”“革命性”“遥遥领先”等无法支持的夸张表达。

## 文件组织

- `public/changelog-<序号>.txt` 每个文件按新到旧保存最多 10 个版本条目，条目继续用独立 `--- / Version / Date / 分类 / 项目符号` 结构。
- 最新文件不足 10 个版本时，新版本写入该文件顶部且索引不变；已有 10 个版本时创建下一序号文件并更新 `changelog-index.json`。
- 除当前最新文件外，其余文件必须恰好包含 10 个版本；文件序号连续，版本在文件之间也必须连续。
- 玩家帮助页按索引先读最新文件，再按需读取更早文件；其他消费者只能读取最新文件的首个版本条目，不能把同文件内十个版本误当成一次更新。
