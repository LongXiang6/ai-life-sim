# 叙事压缩层级、频率与核心叙事历史窗口评估

- 评估日期：`2026-07-25`
- 评估状态：仅盘点与方案比较，未修改任何运行代码、Prompt、协议、存档结构或压缩数据
- 决策问题：压缩系统改为 L1/L2/L3 三层后，L1 应按 5、4 还是 2 轮生成；核心叙事应如何独立取得最近完整叙事

## 一、结论摘要

| 问题 | 结论 |
|---|---|
| 当前是什么机制 | 当前是 **L1-L6 六层**，不是三层。实际覆盖分别为 5、25、125、625、3125、15625 轮。源码顶部的“L3=250轮”等说明已经过期，不能代表实时机制。 |
| 当前核心叙事拿几轮完整原文 | 固定拿最近 **5 轮**，而且这个数直接等于 L1 的 5 轮间隔。 |
| 当前压缩 AI 是否拥有过去历史 | **没有完整拥有。** L1 只看到目标 5 轮及其摘要账本字段；L2-L6 只看到 5 个直接子摘要。它们看不到目标区间之外的过去故事。 |
| 三层方案中推荐哪个 | 推荐 **L1=5、L2=25、L3=125**。它在连续性、调用次数、长期 L3 数量和迁移风险之间最好。L1=4 可作为更细粒度备选；L1=2 不适合作为默认值。 |
| 压缩系统应该多久压缩一次 | L1 每完成 **5 轮**调用一次独立压缩 AI；每 5 个 L1 晋升一次 L2；每 5 个 L2 晋升一次 L3。保持后台执行和失败保留源数据。 |
| 最近完整原文应如何设置 | 不再用 L1 间隔直接决定。压缩系统应返回“全部尚未被成功摘要覆盖的原文”加“可配置的最近细节窗口”，核心叙事只消费该投影。这样以后把细节窗口改成 2、4 或 5，都不会制造历史空洞。 |
| 只有三层的主要代价 | L3 成为最高层后会持续累积。每 1000 轮约产生 8 个（L1=5）、10 个（L1=4）或 20 个（L1=2）L3；不再有 L4-L6 把它们继续合并。 |

## 二、如何打开当前明文日志数据库

当前本地数据库：

```text
D:\AI\ai-life-sim\.data\logs.sqlite
```

当前开发服务器可用，最直接的查看方式是浏览器页面：

```text
http://127.0.0.1:3000/debug-log
```

该页面可以按核心叙事、AI 调用、代理、错误和反馈筛选，展开后查看完整 Prompt、AI 返回、错误、账号 ID、用户名或匿名诊断编号。

命令行查看：

```powershell
cd D:\AI\ai-life-sim
npm run logs:inspect -- --all --limit 20
```

用数据库 GUI 查看：安装 `DB Browser for SQLite`，或在 Cursor/VS Code 安装 SQLite 查看扩展，然后打开上面的 `logs.sqlite`。当前机器没有检测到独立的 `sqlite3` 命令行工具或 DB Browser 安装，因此项目内置页面和 `logs:inspect` 是现成可用的两种方式。

数据库使用 SQLite WAL 模式。服务器运行期间，最新事务可能还在以下两个伴随文件中：

```text
D:\AI\ai-life-sim\.data\logs.sqlite-wal
D:\AI\ai-life-sim\.data\logs.sqlite-shm
```

不要在服务器运行时只复制 `logs.sqlite` 单文件去别处分析；应直接打开原数据库，或连同 `-wal`、`-shm` 一起保留。查看器应以只读方式打开，避免和开发服务器争用写锁。

## 三、当前压缩系统的真实机制

### 3.1 当前职责分布

| 当前所有者 | 实际职责 | 当前问题 |
|---|---|---|
| `SummaryCompressorSystem` | 计算 L1-L6 目标区间、调用独立摘要 AI、校验完成标记、追加摘要、选择最早缺失块重试 | 真正的压缩逻辑在这里，但不拥有完整调度、索引同步和主叙事历史投影 |
| `OrchestratorSystem` | 每轮提交后启动后台压缩、阻止并发压缩、等待压缩完成、构造 `YearEvent`、把结果写回 Engine/Store、同步记忆索引、组装主叙事记忆层 | 核心叙事编排承担了大量压缩系统内部接线 |
| `MemoryLifecycleSystem` | 保存摘要检索索引、选择未被高层覆盖的叶子摘要、格式化长期记忆/相关往事/近期完整原文 | 历史投影规则又分散到另一个系统 |
| `DigestLedger` | 保存每轮可选 digest、重要度和关键事件；向 L1 提供权重，并向主叙事提供高价值“往事回响” | 它是独立的记忆投影，不等同于分层压缩摘要 |

因此，当前“压缩系统”并不是单一职责所有者。未来拆分的重点不是移动一个函数，而是把调度、分层、AI 上下文、结果校验、谱系、失败重试、持久化和历史投影一起收口到压缩系统的公共边界。

### 3.2 当前层级和实际触发点

| 层级 | 直接输入 | 覆盖轮数 | 来源首次齐备 | 当前首次实际生成 | 进入主叙事时的名称 |
|---|---|---:|---:|---:|---|
| L1 | 5 轮完整正文 | 5 | 第 5 轮 | 第 5 轮后台任务 | 近期摘要 |
| L2 | 5 个 L1 | 25 | 第 25 轮 | 第 27 轮 | 中距记忆 |
| L3 | 5 个 L2 | 125 | 第 125 轮 | 第 127 轮 | 远距记忆 |
| L4 | 5 个 L3 | 625 | 第 625 轮 | 第 627 轮 | 纪元概览 |
| L5 | 5 个 L4 | 3125 | 第 3125 轮 | 第 3127 轮 | 一生纵览 |
| L6 | 5 个 L5 | 15625 | 第 15625 轮 | 第 15627 轮 | 一生纵览 |

L2-L6 晚两轮发布，是因为当前实现用 `completedRounds % SUMMARY_INTERVAL >= 2` 作为晋升门。覆盖周期仍分别是 25、125、625、3125、15625 轮，只是高层节点延迟两轮形成。

当前源码文件头写着 L3=250、L4=1250、L5=6250、L6=31250，但实时常量全部是逐层乘 5，因此表格中的 125、625、3125、15625 才是实际值。

### 3.3 每轮运行和失败行为

1. 完整正文先提交到 `narrativeHistory`，随后异步启动压缩管线。
2. 下一次真实推进、预生成快照、读档或开启新人生前会等待当前压缩任务完成。
3. L1 在每个完整 5 轮块结束后生成；如果前面有缺失块，优先重试最早未覆盖块。
4. L2-L6 各取 5 个未被更高层覆盖的直接子摘要；同一次任务中可以继续向上晋升。
5. AI 返回必须有非空正文，并以 `[SUMMARY_COMPLETE]` 结束，否则不建立覆盖节点。
6. 某层失败时保留完整正文或低层摘要，既不伪造成功摘要，也不增加成功统计；后续回合再次尝试。
7. 完整 `narrativeHistory` 不删除；所有已成功摘要节点也继续保存。主 Prompt 只注入未被更高层完整覆盖的“叶子摘要”。

当前不足：失败状态只由缺失覆盖节点间接表达。摘要条目只保存层级、起止轮次、正文、上下文 ID 和时间范围，没有显式 `sourceIds`、尝试次数、最后错误和任务状态；谱系主要靠轮次范围推断。

### 3.4 当前压缩 AI 实际获得的信息

| 调用 | 当前输入 | 当前没有获得的信息 |
|---|---|---|
| L1 | 角色姓名与性别、世界名称；目标 5 轮各自的年龄、时间、完整正文；可选的每轮 digest、整轮重要度、带 0-100 权重和实体的关键事件 | 目标块之前的故事、其他层级摘要、完整世界设定、当前角色状态、核心记忆、伏笔、因果、关系状态、已解决分支。构建器虽然支持已有摘要和玩家选择，但当前调用传入空值。 |
| L2 | 5 个 L1 的轮次范围和摘要正文 | 完整原文、世界/角色信息、目标区间之外的过去历史、记忆与当前状态 |
| L3-L6 | 5 个直接下层摘要的轮次范围和正文 | 与 L2 相同，只改变层级 System Prompt、温度和输出 token 保底 |

所以“压缩 AI 拥有过去历史故事信息”是未来变更，不是当前事实。

## 四、当前核心叙事附带的信息

当前主叙事不是只收到压缩摘要。组装后的信息分为三组：

| 分组 | 当前附带内容 |
|---|---|
| 全局信息 | 世界规则、MOD 世界规则、世界标签、世界校准、精简世界设定、力量体系、原创保护、叙事风格与基调、状态变更指南、篇幅偏好、角色稳定档案、命格与天赋 |
| 记忆 | L1-L6 叶子摘要形成的长期记忆；核心记忆；按实体检索召回的相关往事；摘要账本中高价值且不在近期窗口内的往事回响；最近 5 轮完整正文 |
| 本轮引导 | 当前时间、角色现状、相关子系统状态、最近系统变化、当前情节阶段、可回收伏笔、本轮事件、时间跨度摘要、已触发因果、玩家选择/命运意图、分支限制和本轮导演提示 |

具体历史投影如下：

- `RECENT_NARRATIVE_WINDOW = SUMMARY_INTERVAL = 5`，所以最近完整正文数量与 L1 间隔被硬绑定。
- 长期摘要按 L6 到 L1 选择叶子节点；高层完整覆盖某个低层区间后，低层摘要不再重复注入。
- 最近 5 轮正文不会参与上述摘要覆盖去重，因此最近原文与覆盖它们的 L1/L2/L3 摘要可以同时存在。
- 摘要检索以最新完整叙事为查询，从索引召回相关 L1-L6 内容。
- 摘要账本另行注入有效重要度不低于 40 的旧事件，并排除最近 5 轮，避免与完整原文重复。
- PromptContext 还保存最近 5 轮 `narrativeHistory`。S4 消息策略直接使用格式化后的“近期完整经历”；S3 才把历史放入对话消息，并先与记忆文本去重，因此不是所有策略都会把原文发送两遍。

这说明“减少核心叙事最近完整原文”只影响历史信息中的一个部分，不能等同于减少全部 Prompt，也不能通过缩短 L1 周期来间接实现。

## 五、三层方案量化对比

以下比较统一假设未来只有 L1/L2/L3，每层合并 5 个直接来源，且每次成功压缩需要一次独立 AI 调用。

| 指标 | 三层：L1=5 | 三层：L1=4 | 三层：L1=2 |
|---|---:|---:|---:|
| L1 覆盖/调用周期 | 5 轮 | 4 轮 | 2 轮 |
| L2 覆盖/调用周期 | 25 轮 | 20 轮 | 10 轮 |
| L3 覆盖/调用周期 | 125 轮 | 100 轮 | 50 轮 |
| 一个 L3 周期内调用数 | 25 L1 + 5 L2 + 1 L3 = 31 | 31 | 31 |
| 长期平均每轮压缩调用 | 0.248 | 0.31 | 0.62 |
| 每 100 轮平均压缩调用 | 24.8 | 31 | 62 |
| 相对 L1=5 的调用量 | 100% | 125% | 250% |
| L1 成功时最大未压缩尾部 | 4 轮 | 3 轮 | 1 轮 |
| 每 1000 轮形成的 L3 | 8 | 10 | 20 |
| 若最近完整窗口继续与 L1 绑定 | 5 轮原文 | 4 轮原文 | 2 轮原文 |
| 最近原文字符量相对值 | 100% | 80% | 40% |

“最近原文字符量”只代表历史原文这一段，不代表整个主叙事请求；世界、角色、状态、记忆和本轮引导仍然存在。

### 5.1 L1=5

优点：

- 五轮通常足以容纳一个短期因果段，摘要 AI 更容易看见行动、反馈和后果，而不是只看到两个碎片。
- 固定 System Prompt、网络请求和历史参考上下文的重复次数最低。
- 同样只有三层时，L3 覆盖 125 轮，长期顶层条目增长最慢。
- 与当前 L1/L2/L3 的真实覆盖值一致，未来移除 L4-L6 时不需要重切既有 1-125 轮摘要边界。

缺点：

- 正常情况下最多有 4 轮尚未形成 L1；失败重试时可能更多。
- 如果继续把最近原文窗口绑定为 5，主叙事会保留最多的近期原文字符，并与最近摘要产生部分重叠。

结论：**推荐默认方案。** 压缩频率和最近原文窗口解耦后，它的主要缺点可以单独处理，不需要为了少发一两轮原文而增加压缩调用。

### 5.2 L1=4

优点：

- 比 5 轮更快形成短期摘要，未压缩尾部最多 3 轮。
- L3 恰好覆盖 100 轮，人工阅读和调试时边界直观。
- 如果产品明确希望核心叙事固定携带 4 轮原文，简单绑定下也不会在正常成功路径留下未覆盖尾部。

缺点：

- 压缩 AI 调用量增加 25%，每 1000 轮多产生 2 个 L3 和约 62 个总摘要节点。
- 四轮与五轮的连续性差距有限，节省的也只是主 Prompt 中近期原文部分的 20%。
- 如果职责已经正确解耦，就没有必要仅为了把近期窗口改成 4 而改变压缩边界。

结论：**可用的第二选择。** 只有在更快摘要可见性或 100 轮 L3 边界本身具有产品价值时，才优于 5 轮。

### 5.3 L1=2

优点：

- 一轮之后就能凑齐下一个 L1，未压缩尾部最短。
- 单次 L1 输入最小；如果强行绑定，主叙事近期原文段也最短。

缺点：

- 压缩调用量是 L1=5 的 2.5 倍，固定提示和历史参考被高频重复发送。
- 两轮很容易切断跨轮行动、关系变化和因果后果；后续 L2/L3 会在碎片摘要上继续压缩，累计语义损失风险最高。
- L3 只覆盖 50 轮，只有三层时顶层条目以最快速度增长。
- **不能通过当前实现只改常量得到。** 当前高层门是 `round % interval >= 2`；当 interval=2 时余数只能是 0 或 1，L2 和 L3 永远不会触发。

结论：**不推荐作为默认方案。** 它用大量压缩调用换取很小的未压缩尾部，而这个目标可以通过历史投影正确处理。

### 5.4 与当前六层方案的区别

当前六层在超长周期中的平均调用量为：

```text
1/5 + 1/25 + 1/125 + 1/625 + 1/3125 + 1/15625
= 0.249984 次/轮
```

三层 L1=5 为：

```text
1/5 + 1/25 + 1/125
= 0.248 次/轮
```

移除 L4-L6 只把平均压缩调用量降低约 `0.8%`，因为绝大多数调用来自 L1。三层化的主要影响不是节省 API 次数，而是：

1. 职责更容易收口；
2. 层级含义更简单；
3. L3 不再继续合并，长期主 Prompt 或检索索引中的顶层条目增长更快。

## 六、未来“拥有过去历史”的正确含义

压缩 AI 需要历史背景来理解指代、关系、前因和未解线索，但不应在每次 L1 调用中重复发送全部过去完整正文。后者会让输入量随人生长度快速累积，反过来破坏压缩系统控制上下文的目的。

| 历史提供方式 | 连贯性 | 调用成本 | 风险 | 评估 |
|---|---|---|---|---|
| 每次附带全部过去完整正文 | 最高 | 随轮次快速膨胀 | 重复事实、目标区间污染、长人生超上下文 | 不推荐 |
| 目标源材料 + 当前全部叶子摘要 + 关键历史投影 | 高 | 可控 | 需清楚区分“待压缩源”和“只读背景” | 推荐 |
| 目标源材料 + 仅相关检索命中 | 中 | 最低 | 检索漏召回时缺少时代和关系主线 | 只适合作为补充 |

推荐每次压缩请求分成两个明确区域：

- **待压缩源**：本次 L1 的完整正文，或本次 L2/L3 的 5 个直接子摘要；只有这些内容建立新覆盖关系。
- **历史参考**：目标区间之前的叶子摘要、关键事件、未解决线索和必要世界/角色锚点；只用于消歧和保持因果一致，不得被重新计入本次覆盖范围。

压缩结果仍需保存目标层级、起止轮次、源节点 ID、上下文/时间范围、生成状态、尝试次数和最后错误。完整正文继续由故事历史所有者保存，压缩系统只持有不可变源引用和派生摘要，不建立第二份正文真源。

## 七、建议的职责边界

| 系统 | 修改后应负责 | 不负责 |
|---|---|---|
| 核心叙事 | 消费已组装的世界、角色、当前状态和历史投影；生成本轮正文及相关结构化变化；完成协议校验与提交 | 不决定压缩时机，不拼接 L1/L2/L3，不维护摘要覆盖、重试或检索索引 |
| 压缩系统 | 接收“正文已提交”事件；调度 L1/L2/L3；组装压缩 AI 的源与历史参考；校验、谱系、持久化、失败重试和晋升；输出主叙事可直接消费的历史投影 | 不修改完整正文，不提交角色/世界业务变化，不把摘要当作事实真源 |
| Orchestrator | 保留回合顺序和单写者协调；在正文提交后调用压缩系统公共入口；在存读档和必要边界等待其稳定快照 | 不访问压缩器内部数组，不复制分层或叶子选择算法 |
| 历史账本、核心记忆、伏笔、因果等所属系统 | 继续拥有各自事实和投影，通过公开契约向主叙事或压缩系统提供只读信息 | 不因压缩职责收口而把状态所有权转给压缩系统 |

压缩系统对核心叙事的公共历史投影至少应包含：

1. `summaryLeaves`：按覆盖关系选择的 L1/L2/L3 叶子摘要；
2. `uncoveredNarratives`：所有尚未被成功 L1 覆盖的完整正文，失败多久就保留多久；
3. `recentDetailNarratives`：独立配置的最近完整细节窗口；
4. `retrievalHits`：按当前故事相关性召回的远期摘要；
5. `coverage`：每段内容对应的轮次、源节点和上下文范围，供去重和审计。

主叙事不应自己计算 `slice(-N)`。压缩系统应将 `uncoveredNarratives` 与 `recentDetailNarratives` 合并后按轮次去重，再提供给核心叙事。这样：

- 最近细节窗口设为 2 时，正常 L1=5 周期内仍会自动携带最多 4 轮未覆盖原文；
- 窗口设为 4 或 5 时，会保留更多已摘要但仍有连续性价值的完整细节；
- L1 失败时不会因为固定窗口滑动而漏掉尚无摘要覆盖的旧轮次。

## 八、推荐决策

1. 压缩层级改为三层时采用 `L1=5`、`L2=5×L1=25`、`L3=5×L2=125`。
2. 保留当前“正文提交后后台调用独立 AI、下一关键操作前等待、失败保留源并重试”的运行方式。
3. 如果保留当前 L2/L3 晚两轮晋升的节流行为，应改用“源区间结束轮次 + 2”表达，不能继续用模运算门；否则 L1=2 配置会永久阻断高层晋升。
4. 将最近完整原文数量从压缩间隔中解耦。下一步只需单独比较 `recentDetailNarratives=2/4/5` 对真实 Prompt token、连续性和重复率的影响，不需要再次改变 L1 周期。
5. 压缩 AI 的历史背景采用“目标源 + 叶子摘要/关键历史投影”，不要每次重复发送全部过去完整正文。
