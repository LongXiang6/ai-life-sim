## 三、权重 1-10 的当前衰减算法

### 3.1 权重来源

AI 不决定最终记忆权重。当前本地映射为：

```text
normalizedImportance = clamp(rawImportance, 0, 100)
initialWeight = clamp(roundToInteger(floor(normalizedImportance / 10) + 1), 1, 10)
```

因此 `0-9 -> 1`、`10-19 -> 2`，依次类推，`90-100 -> 10`。粗粒度重要性在没有 0-100 分值时映射为 `LOW=2`、`NORMAL=5`、`HIGH=8`。

高层压缩若把多个来源合并成一条事件，本地会优先选择永久来源，其次选择初始权重最高、锚点更新的来源作为该合并事件的权重锚。权重 10 不交给 AI 再压缩，而由本地原样携带最初记忆事件。

### 3.2 公式

对初始权重 `w=2..9`：

```text
decayInterval(w) = 2^(w - 2)
elapsed = max(0, trunc(currentRound) - weightAnchorRound)
currentWeight = max(0, w - floor(elapsed / decayInterval(w)))
zeroRound = weightAnchorRound + w * decayInterval(w)
forgotten = currentRound > zeroRound
```

这里的间隔由**初始权重**固定，而不是随着当前权重重新选择。例如初始权重 9 的事件每 128 轮下降 1 点，即使已经降到 4，也仍按 128 轮下降下一点。

### 3.3 完整对照表

表中轮数均为相对 `weightAnchorRound` 的偏移量。

| 初始权重 | 每下降 1 点所需轮数 | 首次显示 0 | 首次被判定遗忘 | 当前语义 |
|---:|---:|---:|---:|---|
| 1 | 不执行数值衰减 | 不会显示 0 | 立即不活跃 | 保存在存档数据库，但不进入主动 Prompt |
| 2 | 1 | 第 2 轮 | 第 3 轮 | 极短记忆 |
| 3 | 2 | 第 6 轮 | 第 7 轮 | 短期记忆 |
| 4 | 4 | 第 16 轮 | 第 17 轮 | 较短记忆 |
| 5 | 8 | 第 40 轮 | 第 41 轮 | 中等记忆 |
| 6 | 16 | 第 96 轮 | 第 97 轮 | 中长期记忆 |
| 7 | 32 | 第 224 轮 | 第 225 轮 | 长期记忆 |
| 8 | 64 | 第 512 轮 | 第 513 轮 | 很强记忆 |
| 9 | 128 | 第 1152 轮 | 第 1153 轮 | 极强记忆 |
| 10 | 永久 | 不归零 | 永不遗忘 | 永久记忆，只保留最初压缩结果 |

权重降为 0 的当轮仍属于活跃事件，所以 Prompt 可能看到 `[0，发生时间]`；下一轮才从主动投影移除。这与“衰减为 0 后，下一轮遗忘”的规则一致。

### 3.4 为什么这样计算

1. **高低权重有明显寿命差距。** 线性算法会让 8、9 很快与普通事件趋同；指数间隔让重要记忆明显更耐久。
2. **完全本地、可重复。** 相同存档、锚点和轮次必然得到相同整数，不受模型措辞和随机性影响。
3. **没有小数累积误差。** `trunc`、`floor` 和整数权重使存档、显示、检索门禁保持一致。
4. **永久记忆有硬边界。** 权重 10 不进入后续 AI 再压缩，避免永久事实被高层摘要改写。
5. **压缩与遗忘解耦。** AI 只负责把事实组织到时间段并返回 `sourceIds`；本地负责权重、衰减、归零和是否投影。

### 3.5 当前风险

| 风险 | 说明 |
|---|---|
| 权重 1 的显示语义不直观 | `calculateMemoryWeight()` 对 1 返回 1，但 `isMemoryEventForgotten()` 又立即返回真。数据库、调试面板和 Prompt 需要分别标出“存档保留”和“主动遗忘”。 |
| 合并事件继承最高来源权重 | 一个高权重来源和多个低权重来源被 AI 合成同一事件时，整条合并事件会继承高权重，低权重事实可能被间接延寿。 |
| 9 的寿命很长 | 1153 轮后才遗忘。若大量事件被评为 9，主动记忆规模会持续增长，需要通过评分分布和检索投影控制，而不是偷偷删除。 |
| 当前值不是动态区间算法 | 初始权重 9 降到 8 后仍用 128 轮间隔。若产品想要“当前权重越低，后续衰减越快”，那是另一套算法，不能只改表格说明。 |

当前算法总体符合“低权重快速模糊、高权重显著耐久、10 永久”的目标。建议保留指数框架，未来实现时重点澄清权重 1 的展示状态和混合权重事件的合并规则。

## 四、当前三层四倍压缩运行逻辑

当前实时源码已经完成此前要求的三级四倍结构：

| 层级 | 直接来源 | 覆盖范围 | 形成条件 |
|---|---|---:|---|
| L1 | 4 轮完整叙事 | 4 轮 | 延迟一个完整块后调用独立压缩 AI |
| L2 | 4 个连续 L1 | 16 轮 | 四个来源全部有效且未被已有 L2 覆盖 |
| L3 | 4 个连续 L2 | 64 轮 | 四个来源全部有效且未被已有 L3 覆盖 |

运行顺序：

1. 正文先提交到完整叙事历史。
2. 压缩任务在响应提交后异步运行，关键保存或加载边界等待其稳定。
3. 完成第 8 轮后，1-4 轮首次具备 L1 压缩资格；第 9 轮可使用 1-4 的摘要和 5-8 的完整正文。
4. 完成第 12 轮后，5-8 轮具备 L1 压缩资格；第 13 轮可使用 1-4、5-8 的摘要和 9-12 的完整正文。
5. L2/L3 输入除了本层直接来源，还能读取既有压缩历史作为只读背景。
6. AI 只返回时间段、事件文本、发生时间和来源 ID；本地校验所有来源覆盖后才建立摘要节点。
7. 失败时不建立覆盖，完整正文或低层来源继续保留，后续再次尝试。
8. 主叙事常驻最近 4 轮完整正文，更早内容由成功摘要和检索命中提供。

这一机制已经写入 `core-simulation.md` 和 `logic-tree.md`。`docs/reference/narrative-compression-cadence-evaluation-20260725.md` 是变更前的历史评估，其中六层、五倍制等内容不再代表当前运行事实。

### 5.2 推荐形态

推荐未来新增一个**项目内独立、管理者专用、本机只读的数据查看程序**，而不是把运维内容塞进玩家设置，也不是复制一份数据库：

  -> 使用项目设计变量和排版组件渲染

“独立”指独立入口、独立进程和独立信息架构；数据真源仍只有现有数据库与 TXT。这样可以在游戏开发服务器未运行时查看数据，也不会让设置弹窗承担数据库浏览职责。玩家设置中的“数据统计”不得提供打开此程序、跳转 `/debug-log`、浏览原始 Prompt/响应或查询其他玩家数据的入口。

### 5.4 必要的数据关联

面板要回答“哪个用户产生了哪轮叙事”，至少需要统一关联：

```text
account_id / username / diagnostic_code / device_provenance_id
        -> lifeRunId
        -> round
        -> request_id
        -> call_kind / attempt
        -> narrative-memory node / round archive
```

当前通用日志能关联账号或匿名身份与请求，但 `sessionId` 主要是 `sim-5`、`sim-pregen-5` 这类世界码，不等于 `lifeRunId`。未来实现面板前，应先让每条 AI 调用携带独立 `lifeRunId` 作为本地日志关联字段；它不需要出现在 AI 可见 Prompt 中。

### 5.5 设备来源编号的定义与当前缺口

此次所说的“指纹编码”应落实为独立字段 `device_provenance_id`：由服务端分配、在同一浏览器设备上持久保存的稳定明文编号，用于把该设备来源产生的内容串联起来。它不是 API Key、鉴权凭据或 AI 可见字段，也不替代账号和源 IP。

当前项目中三个相似概念必须分开：

| 字段或概念 | 当前/建议用途 | 能否作为设备来源编号 |
|---|---|---|
| `diagnostic_code` | 服务端随机分配的六位日志定位编号；源码明确声明它不是设备指纹 | 否，现状不能改名冒充 |
| Prompt `fingerprint` | 对部分消息内容做摘要，只在 30 秒窗口内关联重复请求 | 否，它标识内容，不标识设备 |
| `style_fingerprint` | 聚合同一版自定义文风并比较质量 | 否，它标识文风，不标识设备 |
| `device_provenance_id` | 稳定关联设备来源、身份、存档、请求和生成内容 | 是，已由身份初始化请求分配并独立落库 |

每条需要追责的 AI 生成记录至少应同时保存以下明文字段：

```text
device_provenance_id
diagnostic_code
account_id / username / is_registered
source_ip / user_agent / diagnostic_session_id
life_run_id / round / request_id / call_kind / attempt
requested_at / completed_at
完整发送内容 / 完整上游返回 / 最终被采用内容
本地校验结果 / 内容安全判定结果
```

设备来源编号用于快速聚合证据，不能单独证明现实中的自然人责任：本地存储可被清除，浏览器环境可被伪造，共享设备也可能对应多人。责任追踪应联合账号会话、源 IP、时间、请求 ID、设备环境快照和完整生成内容判断。管理者面板应直接展示这条关联链，而不是只展示一个编号。

## 六、权威文档与默认取整规则

### 6.1 当前权威详细程度

当前 `core-simulation.md` 已经描述启动接线、活动成员、回合阶段、AI 协议、原子提交、压缩、存档与恢复；`logic-tree.md` 描述跨系统流程。已有 `$ai-life-sim` Skill 也明确要求：直接运行机制、系统职责或数据契约变化后同步受影响的活动权威事实。

未来每项运行机制的权威章节仍应固定回答：

1. 目标与非职责；
2. 入口和触发时机；
3. 输入、输出与公开契约；
4. 状态所有者和写入边界；
5. 按顺序的正常运行流程；
6. 并发、幂等、重试和回滚；
7. 持久化、恢复与兼容；
8. 日志、统计和可定位字段；
9. 失败时保留什么、丢弃什么；
10. 直接实时源。

这比只写“系统负责压缩”更有用，同时又不在文档复制具体实现代码。

### 6.2 Skill 中缺失的取整要求

现有项目 Skill 没有“计算结果通常取整”的明确规则。建议未来实施时在 `$ai-life-sim` 的必要边界中增加：

> 除非业务明确需要连续量、比例或概率精度，提交到业务状态、存档、AI 协议或用户界面的计算结果应在所属系统边界取整；默认使用四舍五入。使用 `floor`、`ceil` 或 `trunc` 时必须由业务语义决定，并在对应权威运行逻辑中说明。中间计算保留必要精度，只在最终所有者边界取整，避免逐步重复取整造成累计偏差。

需要额外注意负数：`floor(-1.8)=-2`，而 `trunc(-1.8)=-1`。属性允许负值后，取整方式不能互换。概率、倍率、衰减率、动画插值等确需小数的字段，应在字段合同中明确精度和最终显示规则。

实施时已把该规则加入 `$ai-life-sim` 的必要边界，并在评分、费用、Token 预算、权重和界面投影的所属系统边界执行最终取整；概率、倍率、衰减率、分位数和货币换算中间量继续保留合同所需精度。

## 七、设置页四个子选项卡与自定义文风

### 7.1 评估时问题

评估时只有三个 Tab：`个性化 / 模型设置 / 模型调用`。其中“个性化”同时包含阅读排版、动态效果、字体、基础文风、流式显示、缓存统计和数据管理；缓存统计又只展示当前 Provider、模型的 `narrative-main`，看不到格式修复、摘要等其他桶。

基础文风当前是 `default / epic / realistic / poetic` 四选一枚举，没有玩家自定义文本、显式保存或恢复默认行为。

### 7.2 当前四 Tab

| Tab | 内容 |
|---|---|
| 01 阅读与界面 | 字体、段落舒展、动态效果、流式/完整显示等纯展示偏好 |
| 02 叙事偏好 | 基础文风输入、统一的每轮叙事目标字数、叙事相关偏好；不放 API 和缓存统计 |
| 03 模型与调用 | Provider、模型、自己的 API、连接测试、关闭/自动/深入/最大四档思考模式、预生成和模型参数 |
| 04 数据统计 | 只显示当前玩家自己的各调用池 Token、缓存、延迟、每轮/累计费用、自定义 Key 余额和压缩状态 |

第四个 Tab 是玩家自己的模型用量页，不是管理者日志页。不得在这里显示其他账号、设备来源编号、IP、原始 Prompt/响应、数据库表、完整日志，也不得提供打开管理者面板的链接。

### 7.3 基础文风输入

推荐用多行输入框替代四个文风按钮：

- 初始值为空，空值代表项目默认文风。
- 占位提示只给写法示例，不展示项目真实提示词，例如：

```text
例如：采用克制、具体的第二人称叙事；多写行动和对话，少用总结性评价；保持人物反应与既有事实连续。
```

- `保存当前风格`：显式提交当前文本并记录版本。
- `恢复默认`：清空自定义文本，回到项目默认文风。
- 页面应区分“正在编辑”和“当前已生效”，避免输入一半就影响后台预生成。

### 7.4 日志与文风指纹

用户自定义文风用于后续分析时，每轮首次**实际主叙事调用**应由服务端代理在该轮日志中保存一次生效快照；同轮修复只引用该快照，不再从客户端重复上传：

```text
style_source       = default | custom
style_text         = 本轮实际生效的完整明文
style_version      = 保存版本
style_fingerprint  = 对完整 UTF-8 文风文本计算的稳定校验指纹
device_provenance_id = 产生该次调用的设备来源编号
life_run_id        = 当前人生存档
request_id         = 本次 AI 请求
quality_metrics    = 本轮质量、修复与缓存结果
```

`style_fingerprint` 只用于聚合同一版本和比较效果，不能替代 `style_text`；`device_provenance_id` 才负责设备来源关联。两者不能复用字段或互相替代。完整文风明文必须同时保存，文风校验指纹的输入应包含协议版本和完整原文，不能只取前 200 字。

当前代理已有一个 12 位 SHA-256 指纹，但它只取首条系统消息前 200 字和最后用户消息前 200 字，并只在 30 秒内关联重试。它不是文风指纹，不能用于统计玩家自定义文风。

为遵守现有“日志不记录用户操作”的边界，不记录按键、编辑过程、点击保存或打开设置；只在文风真正进入 AI 请求时记录生效快照。

## 八、DeepSeek 缓存池与命中率

### 8.1 官方机制

根据本次读取的 DeepSeek 官方文档：

- 上下文硬盘缓存默认开启，无需客户端开关。
- 只有后续请求完整匹配已落盘的**前缀单元**时才命中。
- 返回统计字段为 `prompt_cache_hit_tokens` 和 `prompt_cache_miss_tokens`。
- 缓存是尽力而为，不保证 100%，闲置后会自动清理。
- `user_id` 用于内容安全、KV Cache 和调度隔离；只允许字母、数字、`-`、`_`，最长 512 字符。
- `user_id` 的官方语义是业务侧用户隔离，不是 AI 可见的故事字段。

因此，“增加缓存池数量”本身不会自动提高命中率。分得过细会让每个池缺少可复用历史；真正决定命中的，是同一隔离范围内的消息前缀是否逐字稳定。

### 8.2 评估时实现问题

当前客户端已有六个广义池：`narrative / summary / worldInit / fate / lowFrequency / adaptation`，并按 Provider、模型、池、调用类型记录统计。问题在于：

1. 客户端生成并发送 `user_id`，代理却写成 `forwardBody.user = body.user_id`；当前 DeepSeek 文档要求字段名仍为 `user_id`。这可能让预期隔离不生效。
2. `user_id` 当前由任务池前缀和 `sessionId` 组成，而主叙事常用 `sim-<worldCode>`，预生成常用 `sim-pregen-<worldCode>`。不同真实用户、不同存档可能得到相同值。
3. 摘要又用 `storySeed` 或世界名称作为 session，不直接使用 `lifeRunId`。
4. 设置页只展示 `narrative-main`，因此用户看不到修复和摘要消耗。
5. S4 虽把全局、记忆、本轮引导分成三条消息，但记忆和状态内容持续变化；动态字段越靠前，后续前缀越难复用。

### 8.3 真实命中数据

| 调用 | Prompt 字符 | 命中 Token | 未命中 Token | 命中率 |
|---|---:|---:|---:|---:|
| 第 9 轮主叙事 | 9,094 | 2,688 | 4,619 | 36.79% |
| 第 10 轮主叙事 | 10,261 | 2,688 | 5,363 | 33.39% |
| 第 10 轮格式修复 | 3,597 | 1,152 | 1,910 | 37.62% |
| 第 10 轮 L1 压缩 | 6,226 | 384 | 3,594 | 9.65% |
| 第 11 轮主叙事 | 13,122 | 2,688 | 7,391 | 26.67% |
| 第 12 轮主叙事 | 13,440 | 2,304 | 7,963 | 22.44% |
| 第 12 轮格式修复 | 2,837 | 1,152 | 1,392 | 45.28% |

主叙事命中 Token 基本停留在约 2.3k-2.7k，但未命中内容随历史增长，命中率自然下降。这个趋势说明首要问题是 Prompt 前缀组织和动态字段规模，而不只是池数量。

### 8.4 推荐分池与前缀策略

DeepSeek `user_id` 建议表示真实业务用户的稳定匿名/账号标识；内部缓存池作为项目自己的调用分类，不再拿任务类型冒充不同用户。

| 内部池 | 隔离和稳定前缀 |
|---|---|
| `narrative-main` | 协议版本 + 固定系统约束 + 稳定世界/角色设定在前，记忆和本轮引导在后 |
| `narrative-repair` | 修复协议版本 + 合法示例在前，只附失败数据和精确错误 |
| `summary-L1` | L1 固定协议和输出 Schema；目标四轮和历史参考在后 |
| `summary-L2` | L2 固定协议；不与 L1/L3 共用易变前缀 |
| `summary-L3` | L3 固定协议；不与 L1/L2 共用易变前缀 |
| `world-init` | 按世界模板版本和初始化阶段分子池 |
| `fate-talent` | 命格/天赋固定协议与内容任务隔离 |
| `adaptation` | 世界适配固定协议与主叙事隔离 |
| `connectivity-test` | 单独统计，不混入产品命中率 |

每个池还应绑定 `provider + model + promptVersion`。稳定字段固定顺序、固定序列化；请求 ID、时间戳、日志编号、`lifeRunId`、`contextId` 等本地关联字段不要插入稳定 AI 前缀。数据统计页同时显示各池和加权总命中率，不能只显示主叙事。

当前实现已经按这一职责边界收口：代理用服务端可信账号 ID 或稳定设备来源编号生成 DeepSeek `user_id`；项目内部另将调用归入 `narrative-main`、`narrative-repair`、`summary-L1/L2/L3`、`world-init`、`fate-talent`、`adaptation`、`connectivity-test` 和低频调用池。数据统计页汇总各池真实 usage；池名不进入 AI 内容，也不再充当业务用户身份。

## 九、思考深度与内容长度

### 9.1 DeepSeek 官方含义

| 控制 | 官方参数 | 作用 |
|---|---|---|
| 思考开关 | `thinking.type = enabled/disabled` | 是否在最终回答前执行内部思考 |
| 思考强度 | `reasoning_effort = high/max` | 控制内部推理投入；`low/medium` 兼容映射到 high，`xhigh` 映射到 max |
| 最终内容 | `content` | 玩家可见回答 |
| 思考内容 | `reasoning_content` | 与 `content` 同级，不应混入玩家正文 |
| 内容长度 | `max_tokens` + 项目篇幅提示 | 限制技术输出空间并引导可见正文篇幅，与推理深度不是同一设置 |

思考模式下，DeepSeek 当前不支持 `temperature`、`top_p`、`presence_penalty`、`frequency_penalty`；为兼容而传入时不会报错，但不会生效。官方当前默认开启思考；普通请求默认 `high`，复杂 Agent 类请求可自动使用 `max`。官方没有值为 `auto` 的 `reasoning_effort`。

### 9.2 评估时项目偏差

- 设置页提供 `disabled + level-1..level-6`，而当前官方 DeepSeek 是 `enabled/disabled + high/max`。
- UI 把六档描述为 512-16384 Token，实际 `REASONING_BUDGET_MAP` 是 1024-32768，显示与请求相差一档。
- 主叙事只要开启思考，无论选择 level-1 还是 level-6，都会被 `resolveCallReasoningEffort()` 强制为 `level-1`。
- 当前请求发送 `thinking.budget_tokens`，没有按现行官方契约发送 `reasoning_effort=high/max`。
- 思考开启时仍构造 `temperature`，还可能发送 `top_p`；对 DeepSeek 当前思考模式没有效果。

### 9.3 当前 UI

玩家看到以下四种思考模式：

| UI 模式 | DeepSeek 请求映射 | 含义 |
|---|---|---|
| 关闭 | `thinking.type=disabled`，省略 `reasoning_effort` | 不启用推理模式 |
| 自动 | `thinking.type=enabled`，省略 `reasoning_effort` | 使用模型和官方服务的默认强度策略；“自动”是项目 UI 语义，不伪造成官方枚举 |
| 深入 | `thinking.type=enabled`，`reasoning_effort=high` | 明确要求高强度思考 |
| 最大 | `thinking.type=enabled`，`reasoning_effort=max` | 明确要求最大强度思考，延迟和输出 Token 通常更高 |

四档均不混入“正文长短”的含义。对不支持这些参数的 Provider，由 Provider 适配层禁用或映射，不把 DeepSeek 私有参数原样发给未知服务。DeepSeek 思考开启时不发送不生效的温度和 Top P；叙事解析只消费最终 `content`，`reasoning_content` 只进入管理者日志和用量统计。

### 9.4 统一的叙事目标字数与 Token 冗余

“叙事内容长度”和“每轮字数”合并为一个设置：`每轮叙事目标字数`。该值只约束玩家可见正文，不包含思考链、标签、摘要和结构化变化区。Prompt 给出目标字数和允许波动范围，`max_tokens` 只作为防止截断的技术上限，不能把二者做成两个互相冲突的玩家设置。

DeepSeek 官方给出的粗略换算是 `1 个中文字符约 0.6 token`、`1 个英文字符约 0.3 token`，实际值以响应 `usage` 为准。建议初始预算为：

```text
T_story = ceil(targetChineseCharacters * 0.6)
T_envelope = P95(同模型最近成功调用的摘要 + 数据区 + 协议标签 Token)
T_variance = max(256, ceil(T_story * 0.25))
T_reasoning = P95(同模型 + 同思考模式 + 同调用类型的 reasoning_tokens)
required_completion_tokens = T_story + T_envelope + T_variance + T_reasoning
max_tokens = roundUpTo64(required_completion_tokens)
```

样本不足时可使用以下启动冗余，之后由真实日志 P95 自动替换：

| 项目 | 启动值 |
|---|---:|
| `T_envelope` | 768 Token |
| 自动/深入 `T_reasoning` | `max(1024, ceil(T_story * 1.5))` |
| 最大 `T_reasoning` | `max(4096, ceil(T_story * 3))` |

`required_completion_tokens` 超过模型输出上限时，应提示该目标字数不可用或降低目标，不能静默截断正文。每轮完成后记录“目标字数、实际正文字数、估算 Token、实际 `completion_tokens`、实际 `reasoning_tokens`、`finish_reason`”，按 Provider、模型、思考模式和调用类型分别滚动校准。只有货币、概率和统计分位数等确需精度的中间值保留小数；UI 字数和 Token 预算最终取整。

### 9.5 自定义 Key 的每轮费用、累计费用与余额

DeepSeek Chat Completion 的 `usage` 当前包含：

```text
prompt_tokens
prompt_cache_hit_tokens
prompt_cache_miss_tokens
completion_tokens
completion_tokens_details.reasoning_tokens
total_tokens
```

其中 `prompt_tokens = cache_hit + cache_miss`，思考 Token 已包含在 `completion_tokens` 中。因此单次实际费用应按下式计算，不能再把 `reasoning_tokens` 加收一次：

```text
inputCost = cacheHitTokens / 1_000_000 * cacheHitPrice
          + cacheMissTokens / 1_000_000 * cacheMissPrice
outputCost = completionTokens / 1_000_000 * outputPrice
callCost = inputCost + outputCost
roundCost = sum(该 round 下主叙事、修复、压缩及其他真实上游调用的 callCost)
```

截至 `2026-07-26`，官方人民币单价快照如下；价格会变化，实施时必须使用带 `model + currency + effectiveAt + sourceUrl` 的服务端版本化价格表，不能把本文数值当永久常量：

| 模型 | 缓存命中输入/百万 Token | 缓存未命中输入/百万 Token | 输出/百万 Token |
|---|---:|---:|---:|
| `deepseek-v4-flash` | 0.02 元 | 1 元 | 2 元 |
| `deepseek-v4-pro` | 0.025 元 | 3 元 | 6 元 |

玩家使用自定义 DeepSeek Key 时，“数据统计”Tab 应显示：本轮费用、当前存档累计费用、按调用池拆分费用、命中/未命中/输出/思考 Token，以及所用价格版本。流式请求必须请求并保存最终 `usage`；上游没返回 `usage` 时显示“未知”，不能写成 0 元。

余额通过项目服务端代玩家请求 DeepSeek `GET /user/balance`，返回：`is_available`，以及每种 `currency` 下的 `total_balance`、`granted_balance`、`topped_up_balance`。余额在打开数据统计页或玩家主动刷新时查询，并设置短时缓存与并发合并，不能随每轮推进或每次渲染都查询。余额是整个 DeepSeek 账号的实时余额，不等于本项目独占预算；UI 必须显示查询时间。金额计算使用十进制定点或最小货币单位整数，避免二进制浮点累计误差。

当前已经用整数纳元按真实 usage 聚合每轮、存档和内部调用池费用；思考 Token 不重复计费。数据统计 Tab 展示价格版本，打开该 Tab 或主动刷新时才经服务端查询自定义 DeepSeek Key 余额，服务端按 Key 和端点进行 60 秒缓存与并发合并。

## 十、主叙事 Prompt 的职责拆分与精简

### 10.1 评估时结构

S4 当前是三条消息：全局信息、记忆、本轮引导。它已经比单条大 Prompt 更清楚，但 AI 仍能看到：

- 世界校准中的人口基数、科技进度等模拟值；
- “当前上下文编号”；
- 大量系统状态、变化指南和协议字段；
- 最近完整叙事、长期摘要、相关记忆和当前事件；
- 要求返回的状态、语义、情节、意图、分支等多组字段。

`contextId` 是世界上下文作用域，不是账号或用户名。它用于本地历史、记忆、伏笔和世界切换隔离；当前把它显示为“当前上下文编号”发给 AI，对叙事生成没有直接价值。

### 10.2 推荐四层边界

```text
本地传输元数据（不进入 AI 内容）
  requestId / account-or-anon / lifeRunId / contextId / round / cachePool

稳定系统契约（缓存前缀）
  角色、输出信封、允许写入边界、最小合法示例

叙事引导区（告诉 AI 写什么）
  必要世界事实、角色当前可感知状态、最近四轮、压缩记忆、本轮事件和玩家意图

变化要求区（告诉 AI 只返回什么变化）
  本轮相关且可写的系统字段、操作类型、条件任务；没有变化的字段全部省略
```

### 10.3 应移出主叙事 Prompt 的内容

| 内容 | 处理方式 |
|---|---|
| 人口基数、科技进度 | 不发送给主叙事 AI；由所属本地系统推进。确需影响故事时，只注入已经形成的可叙事事件，不发送底层进度值。 |
| 当前上下文编号 | 仅作本地作用域和日志关联；AI 只需要世界名称、地点或上下文类型等可叙事信息。 |
| request ID、账号、lifeRunId、缓存池 | 仅放 HTTP/日志元数据，不进入消息正文。 |
| 年龄、日期的规律推进 | 本地计算后只发送本轮显示值，不把日历公式和上下文编号交给 AI。 |
| 派生属性和连锁值 | AI 只返回源变化；所属系统计算后续影响。例如只返回体魄 `+1`，耐力、负重等由本地公式联动。 |
| 无关系统的完整状态 | 相关性系统只投影本轮真正影响叙事的事实和可写字段。 |
| 空变化字段 | 整个字段省略，不输出空数组、空对象、`null` 或重复全量状态。 |

当前中文协议已允许多数数据字段省略，这是可继续利用的基础。问题主要在 Prompt 示例和条件契约仍鼓励模型一次返回过多语义字段。

当前主叙事已经使用四条有序动态消息：`全局信息 / 记忆 / 本轮引导 / 变化要求`。最后一条只列本轮相关可写源字段和条件任务；人口基数、科技进度、上下文 ID 及其他本地传输元数据已移出 AI 可见内容。Prompt 协议版本为 `4.7.0`。

## 十一、失败重试为什么发生，以及应怎样修

### 11.1 评估时真实链路

```text
上游 HTTP 200
  -> 正文与信封可解析
  -> 条件命运意图要求完整语义核心
  -> 数据 Schema 或业务组合规则不满足
  -> 发起 narrative-format-repair 新 AI 调用
  -> 再次输出完整正文、摘要和数据
```

这和 `ai-client` 的网络重试不是一回事。真实日志中所有相关调用的 `attempt=1`，没有发生 429、超时或 HTTP 失败；“一直重试”主要是格式修复调用。

当前修复 Prompt 已经不只是失败原因：它会提醒标准示例、必需标签、空字段省略规则，以及命运意图/分支需要的字段。但仍有两个关键缺口：

1. `quality.validationError` 能得到精确 Schema 路径，却没有加入 `buildNarrativeRepairInstruction()`；模型看到的仍是笼统的“当前命运意图要求完整语义数据”。
2. 正文已经有效时，修复仍要求重新输出完整结果，导致正文重复生成、额外 Token 和内容漂移风险。

### 11.2 推荐修复请求

正文有效、数据失败时只发送：

```text
修复目标：仅返回完整数据区 JSON，不重写正文或摘要
失败路径：语义信号.不可逆
当前值：false
标准规则：叙事语域为“命运”或“传承”时，不可逆必须为 true；否则把语域改为“生活”
本轮条件：当前命运意图仍需完整语义核心与命运意图判定
合法最小示例：只包含本轮需要的完整字段，不列出所有可选系统
原始数据区：<上一版数据>
```

本地保留上一版正文和摘要，把通过严格 Schema 的新数据区与它们组合。若数据修复仍失败，则按现有完整性边界保留玩家可见正文、整包拒绝结构化数据；不能无限重写故事。

当前已使用独立受保护的数据修复 Prompt 落地该链路。每个校验问题包含完整字段路径、当前值、规则和合法示例；正文与摘要已成立时只替换数据区，连续两次数据修复失败后保留正文并整包拒绝结构化变化。

## 十五、按轮服务端被动日志策略

### 15.1 当前消息路径

本次源码核对确认：项目的非流式、流式、修复、压缩和其他 `callAI` 调用最终都向站内 `/api/proxy` 发请求，再由该服务端路由访问托管 Provider、预设 Provider 或玩家配置的自定义接口。玩家的自定义 Key 也随站内代理请求交给服务端转发，不存在浏览器绕开本站服务端直接请求 DeepSeek 的主链路。

```text
玩家浏览器
  -> POST /api/proxy
  -> 项目服务端转发给 AI Provider
  -> 项目服务端接收完整上游响应
  -> /api/proxy 把响应返回玩家浏览器
```

世界初始化另有 `/api/world-init` 服务端路由直接访问上游，但仍然经过项目服务端，且不属于人生回合日志。核心叙事、修复与压缩的按轮记录点应放在 `/api/proxy`。

因此，完整 AI 消息无需再由客户端额外上传。代理端口已经天然看到：

```text
客户端发送给本站代理的完整请求
服务端最终发送给上游的完整请求
上游返回本站代理的完整响应字节
本站代理返回玩家的响应
Provider / model / requestId / usage / status / latency
trace_context 中的 lifeRunId / round / callKind / executionKind
```

评估时 `narrative-round-archive.ts` 已按 `.data/narrative-rounds/<lifeRunId>/round-XXXXXX.txt` 聚合，同一轮的主调用、重试或修复会作为不同 exchange 追加到同一个 TXT；客户端 `recordAICallLog()` 仍会再形成一条重复 AI 调用链。当前实现已在代理返回请求 ID 时跳过客户端重复内容上传，只保留代理被动归档。

### 15.2 目标机制

“每轮触发一次记录”应理解为**每个 `lifeRunId + round` 只有一个逻辑日志会话和一个轮次归档对象**，而不是为了日志再发一次网络请求：

1. `/api/proxy` 收到带轮次上下文的请求时，取得该轮日志对象。
2. 在同一个代理请求内被动写入上游请求原文、响应原文、状态、usage 和耗时，不调用额外日志 API。
3. 主叙事、格式修复、网络重试、当轮触发的压缩分别作为该轮对象中的 exchange 区段，保留调用顺序和 `attempt/callKind`。
4. 同一轮无论有几个 exchange，管理者面板只显示一条轮次主记录，展开后才看到各区段。
5. 客户端不再重复发送完整 Prompt、响应或逐条 AI 调用日志；只在正常代理请求里携带 `lifeRunId`、`round`、`callKind`、`executionKind` 等关联字段。
6. `device_provenance_id` 由服务端从稳定来源上下文取得并附在轮次记录上，不作为新的客户端操作事件上传。
7. 点击、按键、页面导航、输入过程、时间推进按钮和分支按钮本身不记录；它们造成的最终玩家意图若进入本轮 AI 请求，本来就会作为请求内容被动保存。

这不会减少必须保留的内容，只会减少重复网络上传和重复日志行。每个 exchange 的完整原始字节仍保留，今天和昨天的保留/清理策略不变。

### 15.3 被动记录能知道什么

代理可以确定“发给上游什么、上游返回什么、向浏览器返回什么”，但当前结构化解析和最终回合提交发生在客户端，所以代理本身不能百分之百断言某个响应已经被本地状态采用。管理者面板在没有回合提交证据时应标为“已返回”，不能误写成“已采用”。

若未来必须记录最终采用结果，只有两种职责正确的做法：把解析与回合提交迁到服务端，或由客户端在成功提交后只发送一次很小的 `round-commit` 状态事件。按照本次“服务端被动记录”的要求，当前评估优先采用前者的长期方向，不为日志增加逐调用或逐操作上报。

实施后排行榜与邮箱默认开放并拥有独立玩家页面及欢迎页圆形入口；绘图功能仍以服务端 Provider 配置作为真实可用条件。结算评分改由核心唯一所有者计算，世界 Profile、第二人称评语、完整排行榜投影、幂等画像邮件和低频传奇决策均已接线。

## 十七、跨世界结算评分目标算法

### 17.1 世界适配维度的职责

建议在世界初始化或自定义世界定稿时单独调用一次 AI，生成该世界的**评分维度定义建议**，而不是让结算 AI 临时打分。建议结构为：

```json
{
  "profileVersion": 1,
  "worldId": "<稳定世界标识>",
  "dimensions": [
    {
      "id": "<稳定维度 ID>",
      "label": "<世界内可读名称>",
      "description": "<衡量什么>",
      "weight": 25,
      "evidenceKinds": ["<允许的结构化证据类型>"],
      "curveId": "<本地已注册计算曲线>"
    }
  ]
}
```

AI 负责结合世界观提出名称、解释、权重和证据映射；本地评分系统负责：

- 校验维度数量、稳定 ID、名称唯一性和允许的证据类型；
- 将权重取整并校验总和为 100；
- 只接受本地已注册的计算曲线，不执行 AI 生成的代码或任意公式；
- 把完整 `scoringProfile` 和版本固化到存档，保证同一人生可以复算；
- 由结构化选择、关系、成长、突破、影响、旅程和完成事实计算每个维度的 `0-100` 整数分；
- AI 不读取最终待算分数，不得覆盖或补写本地评分。

这种“AI 做世界语义适配、本地做证据计算”的分工，才能同时支持仙侠、赛博朋克、日常、历史等世界，又保持可重放和可审计。仅让 AI 自由生成维度和最终数字会让同一存档重复结算不一致。

### 17.2 70/90 分段公式

设世界适配维度分数为 `D_i`，整数权重为 `W_i`：

```text
raw = clamp(sum(D_i * W_i) / sum(W_i), 0, 100)

if validCompletedLife is false:
    score = min(69, round(raw))
else if raw < 90:
    score = min(89, round(70 + 20 * sqrt(raw / 90)))
else:
    score = round(raw)
```

结果含义：

- 一段正常完成且数据有效的人生至少进入 70 分区间，强化完成感；
- 70-89 仍随原始表现单调增长，不是人人同分；
- 原始分达到 90 后完全取消宽松加成，90-100 每一分都来自真实维度；
- 89 到 90 连续衔接，不出现跨过严格区间的额外奖励；
- 最终玩家分数、维度分和排行榜字段取整数，中间加权值可保留必要精度。

### 17.3 100 分硬门禁

显示 100 前，除 `round(raw) == 100` 外还必须全部满足本地硬门禁；任一失败则最高为 99：

1. 存档存在合法终局，所有必要回合已经原子提交。
2. `scoringProfile`、结构化证据和结算版本完整，可从存档复算出相同结果。
3. 世界配置要求的旅程覆盖、关键选择和高权重成就证据达到该世界的满分阈值。
4. 没有测试、管理调试、直接改写状态、重复事件 ID、回合断裂或校验失败标记。
5. 属性与成就变化都能追溯到合法初始化、命格、回合变化或系统计算来源。

负属性、超过 10 的属性以及没有人为上下限本身都是既定合法设计，绝不能被当成作弊。完整性门禁检查的是“变化是否来自合法状态迁移”，不是把属性强行限制到 `0-10`。

AI 只为结算评语解释已经固定的分项证据，不参与完整性门禁。这样既能让一般玩家稳定获得 70 分以上，又不会通过宽松映射、虚构文案或直接改状态轻易触发 100 分画像。

### 17.4 排行榜资格

按本次表述，目标资格应为：合法完成、完整性校验通过且 `score > 97`。排序固定为：

```text
score DESC
rounds DESC
completedAt ASC
recordId ASC
```

“轮数越大越好”作为同分排序条件。当前额外的 `rounds > 100` 入榜门槛会排除天然短生命周期世界，建议不再作为跨世界统一资格门禁；旅程是否足够应由该世界的评分 Profile 和满分门禁判断。排行榜可提供世界筛选，但全局榜仍遵守上面的统一顺序。

## 十八、第二人称结算评语

分数和维度全部由本地确定后，再单独调用 AI 生成结算评语。输入只包含：固定分数、世界适配维度及分项、结构化大事、已解决选择、终局事实和可引用证据 ID，不要求 AI 重读整部原文或重新判断分数。

推荐返回契约：

```json
{
  "perspective": "micro | macro",
  "review": "<第二人称结算评语>",
  "evidenceIds": ["<实际引用的结构化事实 ID>"]
}
```

评语规则：

- 全文以“你”描述玩家做过的事情，不用第三人称复述角色履历；
- 从真实选择和结果中指出值得肯定的行动，不写无证据的空泛赞美；
- 个人关系、坚持、牺牲或具体抉择证据更强时采用微观视角；社会影响、时代变化或跨区域成就更强时采用宏观视角；
- 先认可最有价值的选择，再描述它如何塑造这一生，最后给出与分数匹配的收束；
- AI 返回失败时由本地按最高分维度和代表大事生成第二人称模板评语，不能让结算页空白；
- 最终评语连同 `evidenceIds` 存入结构化人生记录，排行榜和画像任务复用同一份结果，不各自再生成一版。

## 十九、排行榜、邮箱与满分画像接入目标

### 19.1 排行榜记录

每个账号仍只投影当前最佳合格人生，但投影快照需要扩展为：

```text
username
recordId / completedAt
characterName / worldName / finalAge / rounds
overallScore / scoringProfileVersion
dimensions[]（名称、分数、评语）
endingReview
representativeAchievements[]
portraitAssetId（仅满分且画像完成时存在）
```

排行榜不需要复制完整故事、Prompt 或存档。用户名回答“哪个玩家”，角色、世界、维度、大事和评语回答“哪段人生为什么入榜”。账号 ID 继续作为服务端关联键，玩家榜面展示用户名。

### 19.2 邮箱与画像任务

满分奖励流程应为：

```text
本地分数 = 100 且满分门禁通过
  -> 战绩同步到已登录账号
  -> 以 accountId + recordId 创建唯一画像任务
  -> 服务端绘图 Provider 消费结构化角色信息、世界风格、代表大事和同一份结算评语
  -> 图片写入受控资产目录并建立数据库索引
  -> 对该账号投递一封站内邮件
  -> 邮箱页面展示、标记已读和查看原图
  -> 排行榜投影更新可用的画像引用
```

任务必须幂等，页面刷新、重复同步或 Provider 重试不能生成多封邮件、多张奖励画像或重复扣费。绘图应由服务端异步任务完成，不阻塞结算页；失败状态可重试并在邮箱显示处理中/失败，不伪装成功。

游客达到 100 分时，存档可保留一个未领取的满分资格；只有在该存档后来绑定并同步到账号、且服务端重新通过完整性校验后，才创建画像任务。画像归属于 `accountId + recordId`，不能只按角色名关联。

## 二十、低频多元宇宙传奇彩蛋

### 20.1 来源池

只有同时满足以下条件的人生进入传奇池：分数为 100、满分硬门禁通过、结算和结构化记录完整、画像任务不要求必须成功但来源记录必须仍有效。传奇投影保留来源 `recordId/accountId` 供服务端追溯，对叙事 AI 只提供渲染故事所需的角色、世界、结算评语和代表事件。

### 20.2 频率与冷却

彩蛋按“人生局”抽取，不按回合抽取：

- 每局最多选中一条其他玩家传奇；
- 一次彩蛋出现后，至少连续 3 局不再触发；
- 冷却结束后，每个新人生使用 20% 的确定性抽取门禁，期望约每 8 局出现一次；
- 同一来源传奇对同一玩家设置长期去重，传奇池不足时宁可不触发；
- 抽取结果在新人生开始时固化到存档，读档不能反复重抽。

### 20.3 不抢主线的注入规则

传奇只作为低优先级可选素材。当前轮存在主线推进、玩家明确意图、必须结算的分支、命运事件、格式修复或连续性要求时，本轮不注入；整局没有合适空位也允许完全不展示。

触发时由 AI 把来源事件适配成当前世界能理解的短小载体，例如书页、传说、旧档案、梦境、遗物铭文或路人故事。默认只占一小段，不直接改变主角属性、世界主线或强制选择；玩家主动追查后，才由正常叙事系统决定是否发展为支线。服务端保留“来源人生 -> 目标人生 -> 展示轮次 -> 渲染请求”的完整关联，方便管理者判断频率、重复和叙事影响。
