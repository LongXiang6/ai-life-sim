# 叙事质量 vs Token 优化：调研与对比分析

> 日期：2026-06-22 | 基于 `token-optimization-and-data-unloading.md` v3.0 延伸调研

---

## 一、调研背景

此前的 Token 优化蓝图（`token-optimization-and-data-unloading.md`）发现了"子系统全量传输"的浪费并已修复（方案 B/C）。同时发现 `buildPromptHistory` 是死代码——它不是生产路径。

但用户提出关键问题：**"如果压缩影响剧情流畅度，那优化就没有意义"**。本报告从叙事质量优先的视角，对比两套系统，评估风险，提出建议。


**结论**：确认死代码。自项目创建以来从未被调用过。

### 2.2 它为什么存在？

`buildPromptHistory` 是原始设计中"叙事历史注入 Prompt"的方法。后期 `memoryLifecycle` 系统接管了这个职责，但旧的 `buildPromptHistory` 没有被清理——这是典型的"重构遗留"。类似的模式也出现在本次调研中发现的 `SubsystemRelevanceSystem`（实现了完整功能但核心方法从未接入）。

## 四、叙事流畅度风险评估

### 4.1 生产路径的风险场景

| 风险 | 严重度 | 触发条件 | 具体表现 |
|------|:--:|------|------|
| **早-中期历史真空** | 🔴 高 | 50轮后 | AI 完全不记得第1-50轮发生了什么。如果第5轮人物A救了主角、第30轮A送了信物——AI 不知道A是谁 |
| **伏笔断裂** | 🔴 高 | 有跨轮次伏笔 | `foreshadowing-system` 投放了伏笔，但对应的早期事件在 AI 的"记忆"中不存在。AI 可能："这个伏笔我没有上下文" |
| **人际关系遗忘** | 🟡 中 | 50轮+ | 社交系统的历史互动被压缩到无。人物关系网（NPC-system/civilization/etc）只能通过当前 snapshot 感知，没有互动历史 |
| **世界因果断链** | 🟡 中 | 角色换地图 | 如果角色从一个小镇搬到帝都，早期在小镇建立的声望、仇敌、承诺——AI 全忘了 |
| **检索不可靠** | 🟡 中 | 关键词不匹配 | 检索只按关键词和区域匹配。如果当前叙事没提到某个旧事件的关键词，那个旧事件永远不会被"回忆"起来 |

### 4.2 检索系统的局限性

当前检索逻辑（`retrieveFromIndex` L917-L946）：

```
1. 提取当前叙事中的地区关键词
2. 对检索索引的每条 entry 做：关键词匹配(weight=1) + 区域匹配(weight=2) + 重要度加成(x2 if HIGH)
3. 返回 top 3
```

这个系统在"角色回到旧地点"时很有效（"你回到小镇，想起了当年..."），但在以下场景无效：

- 角色从未离开同一个城市（地点不变，每条 entry 匹配度相同）
- 事件主题和当前叙事关键词无关（角色在战斗，索引里却有"当年和初恋看星星"——永远不会被检索到）
- 非地点型回忆（"你看到了和当年一样的夕阳"——检索不知道"夕阳"）

### 4.3 结论

**当前生产路径的压缩策略对叙事流畅度有显著风险。** 核心问题不在于压缩本身（压缩是必要的），而在于"均匀遗忘"——AI 对所有历史事件一视同仁地遗忘，而不是"记住重要的、忘记琐碎的"。

## 五、娱乐性优先的优化建议

### 5.1 原则

```
娱乐性 > 连贯性 > Token 优化

即：先保证有趣 → 再保证剧情不矛盾 → 最后才考虑省钱
```

### 5.2 立即执行（低风险，不影响叙事）

| # | 建议 | 说明 |
|---|------|------|
| 1 | 保持当前截断阈值不变 | `buildRichPrompt` 的 L1×2 + L2×1 + L3×1 是合理的"即时记忆"窗口 |
| 2 | 保持方案 B/C 子系统过滤 | 子系统数据卸载不影响叙事，只减少无关噪声 |
| 3 | `buildPromptHistory` 保留但不标注为"推荐路径" | 防御性修缮已做，作为备选方案存在即可 |

### 5.3 中期改进（增强叙事连贯性，需调研）

| # | 建议 | 说明 |
|---|------|------|
| 4 | **重要性加权检索** | 当前检索只看关键词匹配。应该在索引时记录每个 L1 摘要的"重要性分数"（`rateImportance` 已有此数据），检索时优先返回高重要性条目——即使关键词不完全匹配 |
| 5 | **伏笔感知检索** | 如果 `foreshadowing-system` 有未回收的伏笔，在检索时强制注入对应时间段的历史摘要 |
| 6 | **关系网记忆** | 每个 NPC 相关的关键事件（第一次见面/冲突/结盟）应永久保留在 prompt 中，不受截断限制 |

### 5.4 长期方向（架构级，单独蓝图）

| # | 建议 | 说明 |
|---|------|------|
| 7 | **叙事重要性图谱** | 不是"均匀遗忘"，而是"基于事件重要性的自适应压缩"——关键事件（转折点/死亡/婚礼）永远保留摘要，琐碎事件（日常吃饭/走路）激进压缩 |
| 8 | **分层 prompt 注入** | 当前是单次 API 调用。考虑改为：先注入历史框架+伏笔+关系网做"世界记忆预热"，再注入当前状态做"即时反应"（two-pass） |

## 六、方案 B/C 对叙事质量的检查

之前实施的方案 B（子系统过滤）和方案 C（变化摘要）是否影响叙事？

| 改动 | 对叙事的影响 | 风险评估 |
|------|------|:--:|
| `getRelevantStates()` 过滤子系统数据 | 子系统 summary 不是"故事"，是数值/状态快照。减少无关系统的数值噪声反而**有助于** AI 聚焦当前剧情 | 低风险 |
| `buildSlidingWindowSummary()` 注入 | 新增的变化摘要给 AI 提供了"最近发生了什么变化"的上下文，**有助于**叙事连贯性 | 正面 |
| `recordState()` / `recordChange()` | 纯内部记录，不直接影响 AI 输出 | 无影响 |

**方案 B/C 不会损害叙事质量，它们是数据管线优化。**

## 七、总结

```
┌────────────────────────────────────────────┐
│                                            │
│  当前压缩系统的问题不是"压缩太多"            │
│  而是"不知道什么不该压缩"                    │
│                                            │
│  ✗ 关键事件（救命、背叛、告白）和           │
│    琐碎事件（吃饭、走路、打招呼）           │
│    被同等对待，统一遗忘                      │
│                                            │
│  ✓ 应该做：重要事件永久保留摘要              │
│    琐碎事件激进压缩                          │
│    伏笔和关系网强制注入                      │
│                                            │
└────────────────────────────────────────────┘
```

`buildPromptHistory`（死代码）的"全量注入"策略在叙事连贯性上有明显优势——AI 知道完整的故事——但 token 成本太高（100轮 ≈ 25k-35k）。生产路径的"均匀截断"策略成本低，但有叙事断裂风险。

**下一步不是二选一，而是设计一个"知道该记住什么"的压缩系统。** 这需要单独蓝图（L3级，涉及 memoryLifecycle + compression + foreshadowing 三个系统的协调）。
