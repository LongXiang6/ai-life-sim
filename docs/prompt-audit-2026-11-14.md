# 主故事 Prompt 审计（2026-11-14）

> 历史审计报告，不参与活动权威裁决。审计对象：`src/mods/mod-engine/server/narrative-system-prompt.ts`（主故事固定资产 9.50.0）与外部参考 `D:\AI\docs\prompt.txt`。

## 0. 审计范围与方法

- 读取当前主故事固定资产全文，按区块统计字符数、示例数量、规则密度和重复表达。
- 读取 `.data/logs.sqlite` 中真实 `narrative-main` 请求与响应，统计实际输出结构。
- 读取外部参考 Prompt 全文，按“角色 / 核心规则 / 输出格式 / 状态继承”进行比较。
- 只比较信息结构、注意力分配和叙事驱动方式，不把外部的属性、寿命、STATE 等具体机制直接移植到本项目。

## 1. 结论

项目 Prompt 的问题不是“规则还不够多”，而是 **结构失衡、角色缺席、规则互相冲突**：

1. 固定 Prompt 约 17,968 字符；真实请求约 24,077 字符。九段完整示例占 12,397 字符（约 51.5%），规则 00–04 占 4,913 字符（约 20.4%），动态数据占 5,439 字符（约 22.6%），返回协议占 1,301 字符（约 5.4%）。
2. 真正属于“角色本体”的 `玩家信息` 只有 1,320 字符（约 5.5%），其中本例的 `背景` 还是空字符串；角色性格、欲望、恐惧、关系没有成为叙事组织中心。
3. 实际 15 轮输出全部是 3 条事件、正文 112–185 字（均值 152.6）、全部 `命运分支: false`。这不是模型不会写，而是 Prompt 在教它写“三事件年度清单”。
4. 用户本次的真实 `篇幅偏好` 是“正文约100字”，但九段示例是 450–650 字，规则又要求年度覆盖 3–5 个时间阶段。三个信号互相冲突，模型只能折中成 150 字左右的两段式事件摘要。
5. 外部 Prompt 约 1,997 字符，没有 few-shot 示例，规则、输出格式和状态块各自只出现一次；它的优势不是“规则更少”本身，而是 **一个清晰角色 + 一条主循环 + 一张紧凑输出表**。项目应借鉴这种信息结构，而不是继续增加规则。

## 3. 结构性问题

### 3.1 九段示例形成“隐藏配额”

九段示例中 8 段恰好 3 条 `事件结果`，1 段 4 条；实际 15 轮输出全部恰好 3 条。固定规则虽然写着“不设置事件数量配额”，但示例是最强的行为示范，模型实际学到的是“每年三条事件”。

这直接造成“事件清单化”：模型先凑三条事件，再把三条事件压成两段正文；正文不再是人物经历，而是事件账本的摘要。

### 3.2 角色没有成为叙事中心

当前 `玩家信息` 只有姓名、性别、种族、背景、属性尺度和天赋技能。没有稳定的“角色核心”：性格、说话方式、在意的人、此刻想要什么、害怕失去什么、与谁有未解决的矛盾。

实际测试中 `背景` 为空，模型只能从出生背景和天赋中推断角色；但出生背景位于输入 5 的控制平面里，前面隔着 18,000 多字符的规则和示例。优先级列表又把“世界规则、已成立事实、年龄与能力边界及返回协议”放在第一位，把“玩家意图”放在第三位，角色从头到尾不是一个独立优先级。

结果就是“事件发生在孩子身上”，而不是“这个孩子在自己的处境里想要、害怕、选择、承担”。

### 3.3 字数、跨度和示例三方冲突

真实 `篇幅偏好` 是“正文约100字”；固定规则要求“年度及多年跨度覆盖约3至5个时间阶段，只展开1至2个关键节点，开头和结尾留下状态差”；九段示例是 450–650 字、3–4 段。

100 字无法同时容纳 3–5 个阶段、1–2 个关键节点、事件账本和状态差。模型只能选择一种妥协：写成 150 字左右、两段、三条事件的摘要。这不是模型偷懒，而是 Prompt 给了不可能同时满足的约束。

### 3.4 事件卡和账本先于故事

固定 Prompt 里“事件卡”出现 21 次；01.6、01.7 用了两大段解释事件卡；九段示例每段都带 `事件卡消费`；实际输出每轮都消费 1–3 张卡。

同时，执行流水线要求“先锁定各阶段的事件结果、属性、天赋线索、命运分支和结局，再把已成立事实编译成正文”。模型自然把正文写成“事件结果的连续摘要”，而不是先有人物场景、再提炼账本。

事件卡本来是软提示，实际却成了结构主轴。

### 3.5 规则重复、否定式堆叠

同一个“宏观编年”要求同时出现在 03 时间尺度、04 正文表达、动态 `时间窗口` 和九段示例说明中；同一个“开头不要复用历史”同时出现在 01.10 和动态 `时间窗口`。

否定词统计：不得 18 次、不能 16 次、不要 11 次、不要求 5 次。模型收到的是一张长长的“禁止清单”，自然趋于保守、模板化、避免犯错，而不是主动写一个好看的故事。

外部 Prompt 的规则以“要做什么”为主：推进时间、遇到分支暂停、每年至少一个事件、属性变化写清楚。它没有用大量否定句描述禁区。

### 3.6 九段示例风格单一，且缺早期人生

九段示例全部是 16 岁以上：少年期、求学期、独立谋生初期、公共职责期、中年治学期、成年离乡、晚年教席、成年医官、晚年守堤者。实际游戏从 0 岁开始，测试覆盖 2–12 岁，正好是示例完全没有覆盖的阶段。

九段示例还共享同一种修辞公式：一个象征物（铜药柜、坐标纸、陶罐、议席徽章、拓片、蜡管、纪念章、阀门钥匙、堤门钥匙）+ 一个转折 + 一个抒情收尾。模型会照抄这个公式，实际输出中的纸鹤、糖罐、奖状、钥匙就是这种仿写。

### 3.7 单条 user 消息放大问题

项目当前把固定规则、九段示例和动态数据合成为一条 `user` 消息发送。外部参考是紧凑的“角色 + 核心规则 + 输出格式 + 状态”结构，更像系统级职责说明。把 18,000 字符规则和示例放进 user 消息，会带来两个后果：

- 模型对 user 消息中的长规则服从度弱于系统角色说明；
- 九段示例作为 user 上下文，容易被当作可模仿的范文，而不是“格式说明”。

这是架构级问题，不建议在第一次修改中同时动；但应作为后续 A/B 项评估。

## 4. 外部 Prompt 的借鉴边界

### 可以借鉴

- 第一段只做一件事：定义 AI 是谁、生成什么、按什么节奏推进。
- 核心规则按“时间 → 模式 → 分支 → 属性 → 寿命 → 事件”分区，每区只出现一次。
- 分支判定写成可执行的几条标准，而不是一句抽象原则。
- 输出格式用一张短模板说明，不靠九段完整范文。
- 状态继承用紧凑块表达，下一轮直接续接。

### 不要照搬

- 六项属性 0–100、隐藏寿命、`<STATE>` 文本块：与本项目 `character-base`、自然寿命、结构化历史不兼容。
- 只按“一年”推进：本项目支持日/月/季/年/多年。
- 纯文本输出：本项目需要 JSON、事件结果、天赋线索和控制平面。
- “每 3–8 年至少一次分支”这类频率配额：会引入新的硬性节奏，需单独立项确认。

## 5. 建议的 V2 结构

目标不是“把 18,000 字压到 2,000 字”这么简单，而是把信息重新分层：**角色 → 事实 → 时间 → 表达 → 软提示 → 示例 → 协议**。

| 区块 | 当前 | 目标 | 内容 |
|---|---:|---:|---|
| 角色与核心循环 | 178 + 分散 | 300–400 | AI 职责、角色中心、想要→阻力→选择→结果 |
| 角色卡 | 无独立区块 | 200–300 | 身份、性格、在意的人、欲望、恐惧、限制 |
| 世界与事实 | 2,835 | 500–700 | 世界规则、历史事实、年龄/能力、未知不补 |
| 时间与篇幅 | 526 + 动态重复 | 150–250 | 按字数自适应的短/中/长结构 |
| 表达 | 962 | 200–300 | 第二人称、场景/对白、反年度报告 |
| 事件卡/控制平面 | 约 900，21 次提及 | 100–150 | 只保留“软提示、可选、可不用” |
| 示例 | 12,397 / 9 段 | 0–250 | 只保留一个最小 JSON 骨架；必要时加一段 100–150 字微示例 |
| 返回协议 | 1,301 | 450–600 | Schema + 一行字段说明 |
| 固定 Prompt 合计 | 17,968 | 1,800–2,800 | 约减少 85% |
| 真实请求合计 | 24,077 | 7,200–8,000 | 动态数据不变时约减少 2/3 |

建议的开头（示意，不是最终文本）：

```text
你是人生模拟器的叙事引擎。你只做一件事：把角色在当前时间跨度里真实经历的人生写成可读章节。
角色是中心：先确定他是谁、此刻想要什么、怕失去什么、与谁有关系；世界是条件，事件是角色选择后的结果。
不要写成事件清单、年度总结、设定说明或示例仿写。
```

建议的核心循环（示意）：

```text
每一轮先找到角色此刻的一个具体愿望、关系或困境，再写他遇到什么阻力、做了什么选择、留下什么可观察的变化。
即使角色年幼，也要有一次符合年龄的主动表达、试探、拒绝或选择；不能让事件只是发生在他身上。
```

### 字数自适应规则（重点）

不要再对所有“一年及以上”统一要求 3–5 个阶段。应按 `篇幅偏好` 决定结构：

- 50–150 字：一个具体场景 + 一个变化；允许只写一件事。
- 200–400 字：2–3 个阶段或一段时间的前后变化；1 个关键场景。
- 500 字以上：3–5 个阶段；1–2 个关键场景；开头结尾有状态差。

这能直接消除“100 字偏好 vs 3–5 阶段”的冲突。

## 6. 改动优先级

### P0：先解决“角色缺席”和“示例配额”

1. 在固定 Prompt 最前面加入“角色 + 核心循环”段，放在世界规则之前。
2. 在动态数据中增加紧凑的“角色卡”投影：身份、性格、在意的人、欲望、恐惧、限制；背景为空时从出生背景、属性和天赋提炼，不新增事实。
3. **删除九段完整示例**；返回协议只保留一个最小 JSON 骨架，不写完整故事。若实测协议漂移，再加一段 100–150 字微示例，不恢复九段。
4. 删除 `02｜执行流水线` 全段，改成一句“先确定已成立事实，正文不与之冲突”；不再要求“先锁定事件结果再编译正文”。
5. 删除 `01.7–01.10`、`01.12`、`03.2–03.4`、`04.2–04.6`、`07` 的字段顺序和批量长段；具体见第 9 节。

### P1：压缩规则和协议

6. 把 01–04 的规则合并去重，保留：世界/历史事实、年龄能力、时间跨度、表达、分支。每个概念只在一个地方出现。
7. 删除动态 `时间窗口` 中重复的宏观编年、开头、反流水账说明，只保留“本轮跨度 + 字数预算”。
8. 返回协议压缩成 Schema + 5 行字段说明；把长解释移到注释/文档，不进入每轮 Prompt。
9. 把否定句改为正向检查清单：角色是否主动选择、场景是否具体、变化是否可观察、是否复述历史。
10. 明确“事件结果可以是 1 条、2 条或更多，按故事需要，不凑三条”。

### P2：架构实验

11. 评估 `narrativePrompt.outputFormat` 从 `text` 改为 `json`，用 JSON mode 降低对示例和协议说明的依赖；先验证各 Provider 兼容性。
12. 评估固定规则从单条 user 消息迁移到 system 消息，动态数据单独 user；保持受保护资产白名单和缓存策略。
13. 评估按人生阶段/世界类型动态选择 1 段示例，而不是固定注入全部示例。

## 7. 验证方案

- 协议回归：`npm run test:narrative-protocol`、`npm run validate:narrative`、`npx tsc --noEmit`、`npm run lint`。
- 真实生成 A/B：同一世界、同一角色、同一种子，各跑 3–5 局；对比：
  - 协议通过率；
  - 每轮事件数分布（是否仍固定 3 条）；
  - 正文长度与 `篇幅偏好` 的匹配；
  - 角色主动性（每轮是否有角色选择/拒绝/表达）；
  - 事件重复度与题材多样性；
  - 分支/结局出现频率；
  - 人工盲评“像人生小说”还是“像事件清单”。
- 先把当前 9.50.0 的 3–5 局输出保存为基线，再改 V2；不要只凭单轮主观判断。

## 8. 建议的下一步

先做 P0 的 1–5 项，不动架构、不动 JSON 契约、不动事件卡机制；用角色卡和极简协议验证“角色是否回到中心、事件是否不再固定三条”。如果 P0 有效，再做 P1 的规则压缩和协议瘦身；P2 的 system/json mode 作为独立实验。

## 9. 奥卡姆剃刀删除清单（补充，优先于前面的目标）

判断标准：**只有解析器、校验器、持久化、事件卡、天赋、属性、批次或设置组件确实依赖的字段语义，才留在每轮 Prompt。** 叙事偏好不靠“再写一条规则”解决；能由数据字段、校验器或质量检查承担的，一律移出。按这个标准，上一版“压到 4,000–5,000 字”仍然太保守，实际可以压到 **1,800–2,800 字**。

### 9.4 必须保留的组件契约（不要再删）

- JSON 顶层字段：`时间定位`、`事件结果`、`事件卡消费`、`天赋表现线索`、`正文`、`命运分支`、`属性`、`自然寿命变化`、`角色死亡`、`结局`；批量时 `故事批次`。
- `事件结果` 四项：`事件`、`成因`、`结果`、`影响`；它是正文的事实依据。
- `事件卡消费`：只列本轮实际采用并写入事件结果的池内卡名；不得用池外卡名。
- `天赋表现线索`：只引用玩家信息中的不透明引用；只在实际使用且有可观察结果时返回；来源回合由引擎记录。
- `属性`：结算后的整数当前值；单项相对输入变化绝对值不超过 3。
- `自然寿命变化`：相对参考年龄的整数年；`角色死亡` 为 false 或 `{死因类型, 死因}`；明确死亡必须同时有 `结局`，且不能有 `命运分支`。
- `命运分支`：本轮新形成的未决方向，2–4 个字符串或 false；玩家已确认的分支输入不是输出分支。
- 批量：最多 10 轮；遇分支/结局/阶段结束停止；每项是完整故事对象；同批卡名只用一次。
- 数据语义：`篇幅偏好`、`叙事称呼`、`文风偏好` 要执行；控制平面是软提示；世界/历史/出生事实优先；玩家输入是尝试，不是成功；未知世界不补全。
