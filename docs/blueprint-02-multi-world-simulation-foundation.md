核心结论：

1. 多世界不等于复制多套完整引擎。项目仍保留一个回合编排权威和一个规范时间权威，各世界通过上下文、局部历法、时间倍率和模拟范围接入。

4. 任意世界观适配依靠显式能力组合和作用域契约，不依靠目录名、固定世界类型或散落的世界观条件分支。

## 2. 多世界目标架构

### 2.1 上下文层级

```text
Campaign
├─ 全局连续状态
│  ├─ 主角身份与基础连续属性
│  ├─ 跨世界记忆、因果与物品身份
│  └─ 旅行状态与全局回合序列
├─ WorldContextRegistry
│  ├─ 世界 / 宇宙 / 位面
│  ├─ 星系 / 星球 / 大陆
│  └─ 区域 / 聚落 / 场景
└─ CurrentContext
   ├─ 当前能力画像
   ├─ 当前空间位置
   ├─ 当前世界实例系统
   └─ 可达的上下文切换出口
```

`WorldContext` 是统一概念，不强制每个世界都拥有星球、国家、地图或物理距离。现实城市、修仙位面、飞船舱室、梦境、网络空间和纯叙事场景都可作为不同种类的上下文节点。

### 2.2 模拟范围

| 模式 | 作用 | 目标执行策略 |
|---|---|---|
| `active` | 玩家当前所在上下文 | 完整运行已启用能力、生成叙事并允许合法状态提交 |
| `background` | 与当前故事仍有因果联系的上下文 | 低频聚合模拟，只生成可追踪事件和必要状态差异 |
| `dormant` | 已访问但暂时无活动因果的上下文 | 冻结详细系统，只保存离开时快照和恢复所需元数据 |
| `closed` | 尚未开放或已永久关闭的上下文 | 不进入运行和 Prompt，仅保留必要索引或结局事实 |

从 `dormant` 恢复时应根据离开时间、世界规则和已确认因果生成一次可解释的追赶结果，不逐回合重放所有细节，也不静默丢失原有事实。

### 2.3 时间权威

- 保留唯一全局 `TimeSystem`，继续拥有规范回合序列、`daysPassed` 和 `totalDays`。
- 每个上下文可声明本地历法、时间显示单位、时间流速和暂停规则，但不能建立第二个竞争的回合提交权威。
- 跨世界移动由切换系统把全局经过时间换算为当地时间，并记录换算证据。
- 不同世界时间流速影响局部模拟推进，不允许直接篡改全局已发生回合。

## 4. 当前未启用系统与目标处置

表中“当前作用”只说明现有代码声称承担的职责，不表示其实现已经满足当前架构、存档、质量或多世界验收。目标阶段见第 6 节，最终拥有系统见第 13 节。

处理类型：

- **保留重写**：职责有价值，但必须按新契约重写后再接入。
- **拆分重组**：当前系统跨越多个权威，不能作为一个系统原样恢复。
- **实例化**：每个世界或上下文拥有独立状态，通过统一契约创建和休眠。
- **混合作用域**：实体身份可跨世界连续，当地效果和位置按上下文计算。
- **世界观插件**：默认关闭，仅由能力画像明确启用。
- **替换旧实现**：保留产品能力，淘汰当前单例或中央大桶实现。

“启用”分为全局常驻、按上下文能力启用和世界观插件启用，不表示所有系统每回合都执行。

| 阶段 | 要启用或改造的系统 | 目标状态 | 完成标准 |

## 8. 必须删除或废弃的旧前提

| 旧前提 | 处理方式 | 原因 |
|---|---|---|
| 单一全局 `WorldConfig` 代表整个存档唯一世界 | 废弃为当前上下文投影；完整数据进入上下文注册表 | 无法表示多世界并存和不同能力组合 |
| 单例 `WorldMapState` | 删除或迁移为按 `contextId` 分区的空间图状态 | 切换世界后会覆盖旧世界位置和区域 |
| 裸 `regionId`、`npcId`、`itemId` | 迁移为全局唯一 ID 或带命名空间引用 | 不同世界会产生 ID 碰撞和错误关联 |
| `planeIndex` 同时表示位面、地图层或空间等级 | 替换为显式 `contextId`、`parentContextId`、`contextKind` 和空间边 | 复用字段无法稳定表达星球、位面、梦境和场景 |
| 地图系统同时拥有资源、人口、势力、外交和 UI | 拆分权威，只保留空间契约和投影输入 | 大桶无法独立休眠、替换或按世界能力关闭 |
| 每回合完整运行全部已访问世界 | 改用模拟范围策略 | 成本随世界数量线性增长，并会制造大量与玩家无关的 AI 和状态变化 |
| 每个世界各自拥有 `TimeSystem` 和回合提交 | 禁止 | 会产生竞争时间线、重复年龄推进和非原子提交 |
| 地图 UI 直接依赖修仙位面、国家或星球等具体 MOD 类型 | 删除深层依赖，改读统一投影 DTO | 同一 UI 无法适配任意世界观，模拟层也会被展示层反向绑定 |
| `adaptation-manager-system.ts` 继续放在 `subsystems/` 并被当作正式模拟系统 | 迁移到叙事引擎 AI 投影层的内部服务目录；保持编排器消费者和会话缓存，不注册运行 ID、不进入玩家系统清单 | 它有真实消费者但没有独立模拟状态，文件位置和名称不应误导系统扫描与恢复计划 |

## 9. 实施决策与验收要求

本文件已经确认目标架构和处置方向，但每个阶段开始前仍必须冻结公开 API、持久化结构、AI 返回 Schema 和跨 MOD 契约；不得把目标批准误当成批量修改代码的授权。

### 9.1 叙事 AI 统一模拟指令

重写后的模拟系统应共享一套中文“系统指令”外壳，再由每个系统声明自己允许的操作和专属字段。该设计扩展现有 `SUBSYSTEM_FIELD_CONTRACTS` 单一真源，不新建第二份 Prompt 字段表、Schema 字段表或系统手写指南。

目标 AI 可见结构：

```text
系统指令:
  - 目标系统: 关系
    目标对象: NPC-全局实体编号
    目标上下文: 当前上下文编号
    操作: 调整关系
    说明: 本轮共同脱险后信任增加
    变更:
      好感变化: 5
      信任变化: 3
    依据事件:
      - 本轮已接受事件编号
```

这只是协议形态示例，最终中文字段、内部名称和 Schema 必须在实施阶段冻结后才能成为公开契约。

#### 9.1.1 通用指令字段

| 通用字段 | 必需性 | 作用 | 约束 |
|---|---|---|---|
| `目标系统` | 必需 | 选择唯一拥有该状态的系统 | 只能使用本轮指南公开的中文系统名 |
| `目标对象` | 按系统必需 | 指向角色、NPC、组织、地点、物品、事件或上下文本身 | 必须引用输入中已有的全局实体 ID；AI 不得自造未知业务 ID |
| `目标上下文` | 上下文系统必需 | 限定变化发生的世界、星球、区域或场景 | 全局连续状态显式使用全局作用域；不得默认写入其他休眠世界 |
| `操作` | 必需 | 表示本条指令属于哪类标准操作 | 只能使用目标系统登记的操作类型 |
| `说明` | 必需 | 保存产生变化的叙事依据和可审计原因 | 不能代替结构化字段，也不能从说明文本反推未提交数值 |
| `变更` | 必需 | 承载目标系统专属字段 | 字段名、类型、范围、枚举和组合关系由系统契约唯一派生 |
| `依据事件` | 可选 | 关联已经成立的事件、因果或意图记录 | 只能引用输入中存在或本轮同包合法创建的事件 |

本地接收层在翻译后补充稳定指令 ID、回合 ID、请求 ID、提交状态和失败原因，用于防重、日志、回滚和存档追踪。这些内部字段不要求叙事 AI 自行生成。

#### 9.1.2 标准操作族

| 操作族 | 标准操作示例 | 适用系统 |
|---|---|---|
| 数值 | 增量、设值 | 属性、健康、寿命、运气、声望、资源等 |
| 实体 | 创建、更新、移除 | NPC、组织、聚落、物品、作品等 |
| 关系 | 建立、调整、解除 | 人际关系、组织关系、外交、商路和空间连接 |
| 状态 | 进入、推进、完成、失败、关闭 | 生命周期、意图、冲突、事件、任务和世界生命周期 |
| 事件因果 | 登记、触发、解决、作废 | 历史事件、延迟因果、预言、伏笔和奇遇 |
| 空间 | 移动、跨界、到达、离开 | 角色位置、NPC 迁移、物品转移和上下文切换 |

操作族只统一语法，不统一业务规则。例如“健康”可以接受生命值增量，但不能接受外交关系操作；“时间”即使拥有数值状态，也不得因此开放给 AI 直接设值。

#### 9.1.3 每个系统必须登记的字段契约

| 契约项 | 说明 |
|---|---|
| 中文系统名 | AI 协议中的唯一名称，严格映射内部系统 ID |
| AI 权限模式 | `只读`、`提议`、`受校验写入` 或 `事件输入` |
| 允许目标 | 当前角色、指定实体、指定上下文、全局状态或系统自有事件 |
| 作用域要求 | 全局、当前上下文、指定上下文或允许跨界 |
| 允许操作族 | 从标准操作族中选择，不允许系统自行发明同义操作 |
| 专属字段 | 中文名、内部名、类型、增量/绝对值语义、范围或枚举 |
| 组合约束 | 必填搭配、互斥字段、前置状态和跨字段一致性 |
| 应用所有者 | 负责预检、公式计算、实际写入、持久化和回滚的 owning system |
| 运行门禁 | 系统必须已注册、当前阶段启用、能力画像允许且本轮可写 |

不是每个系统都必须允许 AI 直接写入，但每个系统都必须显式登记权限模式：

- `time`、`orchestrator`、`simulation-scope-policy`、存档和持久化系统为 AI 只读。
- `context-transition` 只接受玩家意图或 AI 提议，必须由本地检查出口、权限、携带物和时间换算后执行。
- 健康、关系、声望、技能等可以接受受校验写入，但确定性公式和钳制仍由 owning system 计算。
- 历史、因果、预言和奇遇优先接受事件输入，不允许 AI 绕过事件账本直接伪造已经结算的结果。

#### 9.1.4 提交规则

1. Prompt 只注入当前运行、当前相关并且允许 AI 操作的系统契约。
2. 未知系统、未知字段、非法操作、错误实体、错误上下文、越权目标或跨字段矛盾，使本轮全部系统指令整包失效。
3. 本地代码必须先对整包执行权限、Schema、目标存在性、作用域和各 owning system 预检，再进行第一次写入。
4. 多系统变化作为同一个原子提交；任一系统应用失败时回滚本包已经发生的写入。
5. 系统指令失败不裁剪或改写已经合格的正文与摘要；条件任务继续按自己的必需数据规则保持 pending。
6. AI 负责从叙事中表达有意义的变化，系统负责确定性计算、范围限制、状态机合法性、持久化和最终事实。
7. 不因 Prompt 或 Schema 方便而限制故事事件、关系、记忆或因果的语义条数；技术批处理必须保留完整原包和覆盖证据。

每个阶段至少验收：

1. 单世界现有玩家路径无回归。
2. 创建、切换、休眠、恢复和存档还原具有确定证据。
3. 当前世界完整模拟，后台世界只按策略产生聚合结果。
4. 所有事件、关系、记忆、地点和物品引用能够定位到正确上下文与实体。
5. 禁用任一可选能力包或世界观插件后，基础叙事链仍然可运行。
6. 不通过字符数、固定条数、数组位置或容量上限静默删除故事、记忆、因果和世界事实。

## 10. 后续阶段仍需冻结的契约

P0 已在第 14 节冻结并完成世界上下文基础；P1 已在第 15 节冻结历史事件、证据、因果、迁移、提交和持久化边界并进入 MVP。P2—P8 开始前仍必须分别冻结其公开 API、持久化结构、AI 返回 Schema、跨 MOD 契约和迁移方案；不得把 P0/P1 授权扩大为批量恢复后续系统。

P0 实施保持了以下边界：

- 运行策略当前新增 P0 六个外部成员和 P1 唯一外部系统 `historical-event-ledger`；P2—P8 延后系统仍未恢复。
- 当前四个主叙事可写系统没有改变。
- AI 成功协议没有新增第二套写入格式；P1 账本只登记 `event-input`，不进入 `narrativeChange`。
- 存档和公开跨 MOD 契约按 `PD-028/PD-029` 冻结范围修改，并分别提供旧单世界与旧历史动态状态迁移。

## 11. P0—P8 各阶段实际执行系统

本节使用中文名称说明接下来会做什么。内部系统 ID 只作为迁移与开发定位信息保留，不再承担阅读时的主名称；其中需要合并或内部化的旧 ID 不会继续成为最终独立系统，最终目标归属以第 13 节为准。每个阶段只处理表内范围，并继续运行已经通过前序阶段验收的基础能力。

### 11.1 P0 世界上下文基础

P0 是已经完成的第一阶段。它没有增加经济、政治、NPC 或修炼玩法，而是先让一个存档能够安全拥有多个世界、星球和场景，并在它们之间切换。

P0 完成后的直接结果：现有单世界玩法继续可用；同一存档可以安全创建第二个世界或星球，角色可以通过受控流程切换，离开的世界能够后台运行或休眠，记忆、因果、时间和实体不会互相串世界。P0 不恢复旧世界地图，不加入 NPC、经济、政治或超凡玩法。

### 11.2 P1 历史与因果

P1 让世界发生的事情成为长期、可追踪的事实。后续 NPC、政治、经济和灾害都必须以事件账本和因果关系为依据。

| 中文系统或组件名称 | 内部标识 | 系统的详细作用 | P1 具体执行内容 | 叙事 AI 关系 |
|---|---|---|---|---|
| 历史事件账本 | `historical-event-ledger` | 统一保存已经发生、正在进行、被阻止、已解决或已作废的世界事件，以及参与实体、发生地点、原因、结果和证据。 | 建立所有世界共用但按作用域分区的事件真源，为其他模拟系统提供历史依据。 | 登记为 `event-input`；AI 只提供已通过统一协议的语义结果，本地分配 ID、验证作用域并原子提交。 |
| 事件候选提供器 | `EventCandidateProvider`（内部组件） | 接收显式候选，记录 `available/accepted/rejected/expired` 生命周期和通用能力要求；接受前不视为已发生事实。 | 取代旧 `event-pool` 的独立系统、题材预设和事实 Store，由账本拥有候选审计。 | AI 或规则只能提供语义候选；本地对每个目标上下文校验能力并决定接受、拒绝或过期。 |
| 因果图组件 | `CausalGraphComponent`（内部组件） | 在已经存在的事件之间建立原因、条件、阻止、解决或传播关系。 | 取代旧 `causal-simulation` 的正文正则、随机延迟和重复队列，因果边由账本统一保存。 | 不从正文猜测因果；端点、跨世界作用域和证据全部由本地预检。 |
| 延迟因果系统 | `causal-delay` | 管理玩家或剧情已经形成、但要在未来某个条件下兑现的具体承诺和后果。 | 接入历史事件账本；到期后生成待叙事事实，完整回合提交成功后才标记兑现。 | 受控事件输入；不能由 AI 提前宣布尚未满足条件的事项完成。 |
| 叙事编排系统 | `orchestrator` | 把到期事件、当前因果和相关历史装配进本轮叙事，并负责最终原子提交。 | 增加历史事件预检、消费者引用和跨系统快照/回滚顺序。 | 本地编排与提交所有者；不是 AI 可写系统，也不自造历史事实。 |
| 伏笔系统 | `foreshadowing` | 把伏笔与具体历史事件和因果条件连接，确认何时可以回收。 | 伏笔建立、触发和解决都留下对应事件证据。 | AI 可提议建立或回收，系统校验条件。 |
| 剧情结构系统 | `plot-structure` | 根据已经发生的历史和未解决因果调整剧情阶段与张力。 | 使用事件状态而不是正文关键词判断推进、转折和收束。 | 只读约束 AI 叙事结构。 |
| 长期记忆引擎 | `memory-engine` | 把重要历史事件转换为角色和世界的长期记忆。 | 记忆记录事件编号、发生世界、参与实体和结果。 | 消费已经接受的事件事实。 |
| 核心记忆系统 | `core-memory` | 保护决定角色身份、关系和长期目标的重大历史事件。 | 关键事件可以晋升为不可遗忘的全局记忆。 | 只读提供给 AI；晋升必须有事件依据。 |

P1 完成后的直接结果：玩家离开一个世界后，该世界发生过的战争、承诺、灾害、人物死亡或重大转折不会只存在于一段正文中；系统能够知道事情为什么发生、是否解决、会影响哪个世界以及什么时候继续兑现。

### 11.3 P2 NPC 与社会关系基础

P2 让叙事中的人物从“当轮临时名字”变成具有身份、位置、目标、记忆和关系的长期角色。

| 中文系统名称 | 内部系统 ID | 系统的详细作用 | P2 具体执行内容 | 叙事 AI 关系 |
|---|---|---|---|---|
| NPC 属性系统 | `npc-attribute` | 为每个重要 NPC 保存全局身份、年龄、稳定属性、状态和当前位置。 | 使用全局实体 ID 创建 NPC，并将属性和当地世界规则分开保存。 | 受校验写入；AI 可提出 NPC 创建和属性变化，系统负责合法化。 |
| NPC 行为系统 | `npc-behavior` | 根据 NPC 的目标、状态、关系、记忆和环境决定其行动；普通人物优先使用本地规则，关键事件才使用 AI 增强。 | 建立当前世界完整决策和后台世界低频聚合决策。 | 提议；AI 为关键 NPC 提供语义行动，本地检查条件和成本。 |
| NPC 记忆系统 | `npc-memory` | 保存每个 NPC 自己知道的事实、主观印象、情绪和关系经历，使不同人物拥有不同认知。 | 连接历史事件、关系图和世界作用域，并采用可追踪语义合并。 | 事件输入；AI 可表达人物如何理解事件，系统保存事实来源。 |
| 关系系统 | `relationship` | 统一保存人与人、人与组织以及组织之间的关系类型、好感、信任、羁绊和冲突。 | 从文化大桶拆出为通用关系图，允许关系跨世界保持或按当地身份变化。 | 受校验写入；支持建立、调整和解除关系。 |
| 长期记忆引擎 | `memory-engine` | 保存主角视角下对 NPC、关系和事件的长期认识。 | 与 NPC 自身记忆区分，避免所有人物共享同一份全知记忆。 | 消费叙事和已提交事件。 |
| 核心记忆系统 | `core-memory` | 保护关键 NPC、核心关系和不可遗忘的人生事件。 | 核心关系跨世界继续可检索，并保留原发生地点。 | 只读提供给 AI。 |
| 子系统相关性系统 | `subsystem-relevance` | 判断本轮哪些 NPC、关系和记忆真正相关。 | 只加载当前场景和因果相关人物，后台人物不逐个进入主叙事 Prompt。 | 只读。 |
| 世界实体系统 | `world-entity` | 为 NPC 所属的国家、派系、家族和聚落提供稳定组织身份。 | 让 NPC 关系和行为可以引用真实组织，而不是只保存组织名称文本。 | 事件输入。 |

P2 完成后的直接结果：玩家再次遇见旧人物时，对方能够保留年龄、立场、记忆、信任和关系；玩家离开后，重要 NPC 可以继续以低成本方式生活和行动，而不是彻底冻结或每轮都调用 AI。

### 11.4 P3 空间、地理与资源

P3 恢复地图能力，但不会恢复旧的单例大地图系统。它先建立统一空间和地理数据，再由界面按世界类型投影成城市图、星图或位面图。

| 中文系统名称 | 内部系统 ID | 系统的详细作用 | P3 具体执行内容 | 叙事 AI 关系 |
|---|---|---|---|---|
| 地理系统 | `geography` | 保存地形、区域地理属性、板块或空间结构变化，以及这些变化影响的地点。 | 按世界上下文实例化地理状态，只负责地理事实，不拥有势力、人口或地图界面。 | 事件输入；AI 可描述地理变化，本地确认影响节点。 |
| 自然资源系统 | `natural-resource` | 保存资源种类、空间分布、储量、再生、消耗和危机状态。 | 将资源挂载到空间节点，并为经济、产业、冲突和物品系统提供统一读取接口。 | 事件输入；确定性储量计算由系统完成。 |
| 地图投影系统 | `map-projection` | 把空间关系图、地理、已知地点和探索信息转换成玩家当前世界适合的地图数据。 | 提供地图、星图、位面图和抽象场景导航的统一投影，不保存模拟真源。 | 只读；不接受 AI 状态写入。 |
| 旧世界地图系统 | `world-map` | 旧实现同时管理地图模板、区域、资源、人口、势力和外交，职责过多且只能表示单一世界。 | 只迁移仍有价值的区域、邻接和位置数据，迁移完成后退出运行，不原样恢复。 | 禁止写入。 |
| 空间关系图 | `spatial-graph` | 提供所有地点和世界之间的层级、邻接和可达关系。 | 接入地理属性、资源节点和地图投影。 | 事件输入。 |
| 上下文切换系统 | `context-transition` | 负责角色和实体在空间节点之间实际移动。 | 使用统一路径、出口和跨界规则执行移动。 | 提议后本地执行。 |
| 世界实体系统 | `world-entity` | 提供国家、组织、聚落和商路等具有位置的实体。 | 将世界实体挂载到空间节点，移除地图系统对这些状态的所有权。 | 事件输入。 |

P3 完成后的直接结果：玩家可以查看符合当前世界观的地图或导航，角色、NPC、资源、聚落和事件都能明确定位；从星球移动到星球、从位面进入位面和在城市内换场景使用同一套空间契约。

### 11.5 P4 通用成长与社会评价

P4 建立任何世界观都能使用的成长体系。现实技能、科技能力、魔法、修炼和特殊天赋共享基础契约，但不共享具体名称与规则。

| 中文系统名称 | 内部系统 ID | 系统的详细作用 | P4 具体执行内容 | 叙事 AI 关系 |
|---|---|---|---|---|
| 技能系统 | `skill` | 保存技能定义、学习来源、熟练度、使用记录、掌握状态和成长结果。 | 从单一超凡技能逻辑中拆出通用成长内核，支持任意世界观技能。 | 受校验写入；AI 可提出新技能和经验变化，系统验证来源和规则。 |
| 个人能力系统 | `personal-ability` | 保存天赋、长期稳定能力、潜力、学习限制和能力修正，与具体技能熟练度分开。 | 与技能系统重新划分边界，避免两个系统重复拥有经验和等级。 | 受校验写入；稳定能力变化必须有事件依据。 |
| 成就系统 | `achievement` | 根据可验证条件记录角色完成的重要目标、里程碑和成就进度。 | 使用历史事件账本判断条件，区分全局成就与当地世界成就。 | 事件输入；AI 可提出候选，最终解锁由本地验证。 |
| 声望系统 | `reputation` | 保存人物、组织、地区和文化对角色的不同评价，而不是只有一个全世界共享的声望值。 | 建立作用域化声望，允许同一角色在不同世界、组织中评价不同。 | 受校验写入；必须指定评价主体、维度和原因。 |
| 角色基础系统 | `character-base` | 提供技能和能力可能影响的四项基础属性。 | 接收具有来源的成长修正，不让技能系统直接夺取基础属性所有权。 | 受校验写入。 |
| 子系统相关性系统 | `subsystem-relevance` | 决定本轮哪些技能、能力、成就和声望需要发送给叙事 AI。 | 防止角色能力越多，Prompt 就无限膨胀。 | 只读。 |
| 历史事件账本 | `historical-event-ledger` | 为技能获得、成就解锁和声望变化提供可验证事实。 | 所有长期成长结果关联学习、使用、胜利、失败或评价事件。 | 事件输入。 |

P4 完成后的直接结果：玩家在现代世界可以学习医学或驾驶，在魔法世界可以学习法术，在修仙世界可以学习功法；成长记录、来源和结果能够被叙事真实引用，而不是只在正文里说“学会了”。

### 11.6 P5 生命、健康与死亡

P5 补全角色从成长、受伤、衰老到死亡后的完整生命过程，同时允许机器人、不死者、群体意识等世界使用替代规则。

| 中文系统名称 | 内部系统 ID | 系统的详细作用 | P5 具体执行内容 | 叙事 AI 关系 |
|---|---|---|---|---|
| 健康系统 | `health` | 管理生命值、体力、精神、疾病、伤势、恢复过程和死亡检测。 | 把身体状态与当地环境、医疗、种族和时间规则连接，并保留跨世界连续性。 | 受校验写入；AI 可提交伤病和恢复事实，死亡仍需系统确认。 |
| 生命阶段系统 | `life-stage` | 根据角色种族、形态和世界规则管理幼年、成年、衰老或其他阶段变化。 | 淘汰固定八阶段前提，改为可配置的阶段状态机。 | 状态提议；本地根据年龄和前置条件确认迁移。 |
| 年龄衰减系统 | `attribute-decay` | 计算年龄、生命阶段和身体状态对基础属性产生的长期修正。 | 只产生带来源的属性修正，不直接覆盖角色基础属性。 | AI 只提交语义事件；数值由本地公式计算。 |
| 死后叙事系统 | `post-death-epilogue` | 处理角色死亡后的世界变化、生平总结、继承、墓志铭及可选灵魂、复活或转世流程。 | 改为能力驱动的死亡后流程，不强制所有世界采用同一种死后规则。 | 条件叙事；终态和继承结果必须结构化提交。 |
| 寿命系统 | `lifespan` | 保存最大寿命、寿命突破和增减。 | 与生命阶段、健康和当地时间规则共同决定死亡风险。 | 受校验写入。 |
| 角色基础系统 | `character-base` | 保存被健康、衰减和生命阶段修正的基础属性。 | 聚合伤病和衰减修正，但保留自身状态所有权。 | 受校验写入。 |
| 时间系统 | `time` | 提供年龄增长和健康推进所需的规范经过时间。 | 所有生命系统统一读取同一个回合时间。 | 只读。 |
| 历史事件账本 | `historical-event-ledger` | 保存出生、疾病、伤势、突破、死亡和继承等生命事件。 | 让死亡和重大健康变化成为可追踪历史，而不只是正文描述。 | 事件输入。 |

P5 完成后的直接结果：伤势和疾病会持续、恢复或恶化；年龄和生命阶段会真实影响角色；死亡不再只是文本结尾，而能留下世界变化、关系后果、继承和完整人生收束。

### 11.7 P6 人口、聚落、职业、物品与经济

P6 建立日常生活和宏观经济。各模块可以独立关闭，因此无货币、无城市或群体意识世界不需要强行套用现代经济。

| 中文系统名称 | 内部系统 ID | 系统的详细作用 | P6 具体执行内容 | 叙事 AI 关系 |
|---|---|---|---|---|
| 人口系统 | `population` | 管理人口规模、群体构成、出生死亡、迁移和城镇化等聚合变化。 | 按世界和区域进行低成本聚合模拟，不为每个普通人口创建完整 NPC。 | 事件输入；确定性人口计算由本地完成。 |
| 聚落系统 | `settlement` | 管理城市、村落、基地、空间站或其他定居空间的繁荣、安全、设施和发展状态。 | 把聚落实现为一种可选空间实体，不假设每个世界都有永久城市。 | 受校验实体写入。 |
| 职业与工作系统 | `work` | 管理角色的社会角色、工作任务、职业进展、报酬、满意度和晋升。 | 将“职业”和“收入”拆为可替换规则，支持无货币劳动、任务制或身份职责。 | 受校验写入；系统验证前置条件和报酬规则。 |
| 物品系统 | `item` | 管理物品身份、所有权、背包与容器、装备、位置、耐久和状态。 | 建立全局物品 ID和跨世界携带规则，超凡物品以后作为扩展接入。 | 受校验写入；支持创建、转移、更新和移除。 |
| 经济系统 | `economy` | 组合生产、交换、货币、市场、价格、税收和财政能力。 | 拆分旧经济大桶，只有世界能力画像声明相应能力时才启用模块。 | 事件输入为主；价格和税率等结果由本地模型计算。 |
| 空间关系图 | `spatial-graph` | 为人口迁移、聚落、商路、工作地点和物品位置提供空间基础。 | 校验来源地、目的地和运输路径。 | 事件输入。 |
| 世界实体系统 | `world-entity` | 提供组织、聚落和商路等经济参与者。 | 将实体身份连接人口、工作和经济状态。 | 事件输入。 |
| 历史事件账本 | `historical-event-ledger` | 保存迁移、市场危机、职业变化、物品获得和聚落发展等事件。 | 为经济变化提供原因和后果证据。 | 事件输入。 |

P6 完成后的直接结果：角色可以拥有真实物品、职业和工作进展；城市或基地会发展，人口会迁移，市场和资源会发生变化；但不适用的世界可以只启用其中一部分。

### 11.8 P7 社会文明、政治、科技与生态

P7 是大型组合阶段，实际实施时仍应按能力包拆成多个小批次。这里的系统不会整包强制启用。

| 中文系统名称 | 内部系统 ID | 系统的详细作用 | P7 具体执行内容 | 叙事 AI 关系 |
|---|---|---|---|---|
| 纪元系统 | `era` | 根据当地历史和历法标记时代、阶段和时代转换。 | 改为每个世界独立实例，不拥有全局时间。 | 状态提议；迁移由当地时间和事件确认。 |
| 天象周期系统 | `celestial` | 管理日月星辰等自然周期、天象阶段和相关环境事件；玄学运势部分延后到 P8。 | 拆出不依赖神秘力量的通用天象能力。 | 事件输入。 |

| 生态系统 | `ecology` | 管理物种、种群、生物多样性、濒危、灭绝和入侵扩散。 | 连接空间、气候、资源和历史事件，支持后台聚合模拟。 | 事件输入。 |

| 家族系统 | `family` | 管理亲属、配偶、子女、继承和家庭事件。 | 作为通用关系图和生命周期的扩展，不固定家庭形式。 | 受校验关系与事件输入。 |

| 产业系统 | `industry` | 管理产业类型、生产率、技术采纳、资源需求和稀缺影响。 | 与经济和资源系统明确分工，不重复拥有资源储量。 | 事件输入；生产率由本地计算。 |

P7 完成后的直接结果：世界可以形成自己的文化、家庭、教育、政治、法律、外交、技术、产业、气候和生态变化；现实、古代、科幻、末日或无国家世界只启用适合自己的能力包。

### 12.6 当前判断结论

1. 已立即删除：金手指系统。
2. 迁移后删除旧实现：旧世界地图、旧事件池、旧因果模拟。
3. 降为内部齿轮：叙事解析、相关性筛选、世界观文本适配、记忆管线、地图投影、世界初始化、命名服务、死后流程和冲突状态机。

5. 延后系统当前没有进入正常回合，因此“现在没有运行消费者”本身不能证明应删除；只有确认未来也没有独立责任或明确消费者时才删除。

### 14.3 持久化与兼容策略

1. `mod-world` Store 保存完整 `contexts` 注册表和 `currentContextId`，同时继续提供 `worldConfig/entities/worldCode/...` 当前上下文投影，供现有页面和旧调用方使用。
2. 当前投影的每次合法写入必须同步回当前上下文实例；切换时先保存离开上下文投影，再一次性投影目标上下文。
3. 旧存档只有单一 `worldConfig` 时，在迁移中创建一个首上下文，保留原配置、实体、标签、校准、世界编码、纪元和初始化状态；不得要求玩家重开。
4. 旧世界实体和区域保留原本地 ID 作为迁移元数据，运行主键改为带上下文命名空间的全局 ID，并同步更新商路、势力区域和地点引用。
5. 角色 Store 新增稳定全局角色 ID；旧存档首次迁移时生成并持久化，之后不得因改名、切换世界或读档改变。
6. 编排器快照保存当前 `contextId` 和内部叙事子系统状态；恢复时世界 Store 先恢复完整注册表，再恢复编排器和当前世界投影，任一核心步骤失败整包回滚。

### 14.4 运行与 AI 边界

1. P0 已将世界上下文注册表、上下文能力画像、空间关系图、上下文切换、模拟范围策略和世界初始化加入 MVP 外部运行成员；主叙事可写名单仍只有基础属性、寿命、气运和道德。
2. `time` 和 `orchestrator` 继续保持单例。上下文系统只能读取规范时间、选择运行范围和请求切换，不能建立第二时间线或第二提交链。
3. 当前 `active` 上下文运行完整 MVP 链；`background` 只允许明确登记的聚合系统；`dormant` 与 `closed` 不进入完整回合、Prompt 或状态写入。
4. 世界上下文注册表、能力画像、模拟范围、时间和编排为 AI 只读；空间图和世界实体为事件输入；上下文切换和世界初始化为提议。P0 不向主叙事开放任何新可写字段。
5. Prompt 世界视图必须明确当前上下文编号、类型和范围；叙事历史、摘要、账本、伏笔和延迟因果必须保存发生上下文。旧世界事实可以检索，但当地伏笔和当地因果不能在无关世界自动触发。

### 14.5 P0 非目标

- 不恢复 NPC、历史事件账本、地理资源、经济政治、文化生态或世界观插件。
- 不实现逐后台世界的完整回合重放；P0 只建立范围与当地时间结算契约。
- 不把 `worldCode`、世界名称、角色名称或六位诊断编号继续当作稳定业务主键。
- 不为了多世界复制第二个 `TimeSystem`、编排器、存档聚合器或叙事调用链。
- P0 不新增玩家页面；玩家可见入口在定版页面方案获批后接入，本阶段以公开运行 API、存档能力和确定性验收证明底座可用。

### 15.2 唯一公开事实契约

| 概念 | 冻结语义 |
|---|---|
| `historicalEventId` | 存档内稳定事件编号，由本地账本分配；AI、世界名称和旧数组位置不能替代 |
| `eventScope` | `global/context/travel/cross-context`；当地事件必须列出稳定 `contextIds`，跨界事件显式包含多个上下文 |
| `eventStatus` | `scheduled/active/occurred/prevented/resolved/void`；每次变化追加 transition，不覆盖或删除旧状态证据 |
| `evidence` | 指向已经接受的叙事回合、关键事件、系统提交、延期承诺、伏笔、候选或迁移来源；不得用未验证正文猜测补全 |
| `causalEdge` | 连接两个已存在事件的 `causes/enables/blocks/resolves/amplifies/propagates` 关系；端点、作用域和证据由本地预检 |
| `candidate` | 可发生事件的内部提议与审计记录；`available/accepted/rejected/expired` 只表达候选生命周期，不等于世界事实；可选 `requiredCapabilities` 必须由 owning system 对每个目标上下文逐项验证，空数组表示世界观中立 |
| `historicalEventBatch` | 事件创建、状态迁移、证据和因果边的统一原子提交单位；任一非法使整批失败 |

事件可同时保存已验证的稳定实体 ID、空间节点 ID和无法解析为业务 ID 的人物或组织标签。标签必须明确是标签，不能伪造全局实体。

### 15.3 精简和迁移边界

1. MVP 外部运行成员只新增 `historical-event-ledger`，P1 完成后外部运行系统为 13 个、总运行系统为 25 个。
2. 旧 `event-pool` 系统 ID 与文件已删除，不进入 manifest subsystem、runtime、Prompt 或 `narrativeChange`；替代组件 `src/mods/mod-history-dynamics/components/event-candidate-provider.ts` 只在账本内部构造候选和追加式候选审计。
3. 旧 `causal-simulation` 系统 ID 与文件已删除；替代组件 `src/mods/mod-history-dynamics/components/causal-graph-component.ts` 不保留正文关键词正则、独立 pending/resolved 队列、固定年代容量、随机 3—15 年延迟或自动到期解决，只构造账本拥有的显式因果边。
4. 旧已触发事件池条目迁为已发生事件；未触发条目迁为候选；过期未触发条目保留为 `expired` 候选审计，不伪装成事实。
5. 旧待处理和已解决因果记录分别迁为 `active/scheduled` 与 `resolved` 事件，保留旧 ID、年份、完整捕获描述和结果；旧计数与处理年份进入迁移证据。
6. 迁移和正常运行均禁止固定容量、FIFO、字符截断或数组位置淘汰。技术批处理只延后消费，不删除真源。

### 15.4 AI、提交与回滚边界

1. `historical-event-ledger` 在 `SUBSYSTEM_FIELD_CONTRACTS` 登记为 `event-input`，但不加入旧四系统 `narrativeChange` 白名单。
2. P1 不修改主叙事成功协议。只有完整结构化数据区已通过 Schema、命运条件和普通状态变更整包预检后，本地才可把摘要、关键事件、语义信号、延期因果和伏笔结果翻译为账本批次。
3. AI 不能自造事件 ID、证据 ID、状态提交结果、显式跨界因果边或未满足条件的解决结果。跨界因果先由本地系统或账本公开 API 提交。
4. 编排器在普通状态写入前捕获外部系统、内部连续性系统和必要 META 快照；随后提交普通变更、历史批次、延期因果、伏笔、剧情和记忆引用。任一步失败恢复全部副作用并拒绝依赖 META。
5. 合格正文与摘要不因结构化副作用失败而丢失；摘要账本可以继续记录自身合格摘要，但不得把失败的历史批次伪装为已提交世界事实。
6. 预生成和预览使用同一快照/恢复机制，不能污染真实账本、候选、因果边、伏笔、记忆或延期状态。

### 15.5 持久化和读取策略

1. `useHistoryDynamicsStore` 是运行事实权威；Store `schemaVersion: 2` 追加保存 `events/transitions/evidence/causalEdges/candidateAudits/migrationMetadata` 六类完整状态。编排器持久化快照通过账本的 `capturePersistenceState/restorePersistenceState` 保存，以便每个存档独立恢复。
2. `collectState()` 只返回全局或作用域显式包含当前上下文、仍需消费的 `scheduled/active` 视图及统计；它通过只读索引复用事件状态、证据和因果边，不调用完整持久化克隆，也不对每个事件重复全表扫描。事实正文进入主叙事时由确定性投影器读取该视图，禁止经过后台世界观适配器改写。
3. 查询 API 可以按事件 ID、上下文、状态、实体、标签、地点、tag、证据、迁移和因果端点读取完整历史，并读取带关联总数的事件详情。公开查询默认 `limit: 100`、最大 `500`，通过 `offset` 分页；分页只限制单次返回，不改变或删除事实。
4. 新存档初始化空账本；旧 Store v1 和旧 collected state 仅迁移该存档自带的 `event-pool/causal-simulation` 状态。已触发条目、未触发或过期候选、pending/resolved 因果分别进入事件、候选审计、迁移证据和 `legacyPayload`。若浏览器持久化先于 world Store 水合，运行注册后必须把临时 global 的 v1 历史一次性重绑到该存档原当前上下文；不得串入第二世界或另一个存档的浏览器残留。
5. v2 恢复先严格校验六类数组、重复 ID、状态链、证据/因果端点、候选审计链、世界/实体/地点引用和 scope 一致性，再一次性替换 Store。显式读档与浏览器/Zustand 当前 Store 水合必须共用该校验；损坏水合状态保留供诊断但隔离于查询、提交和存档，不能静默清空。当前 v2 畸形数据和未知未来版本必须拒绝。存档恢复时账本、世界上下文与编排器当前上下文必须共同成功；任何核心不一致都保持原游戏并整包失败。
6. 记忆、核心记忆、伏笔和剧情结构只持久化已接受事件 ID：`historicalEventIds`、`plantedFromEventIds/resolvedByEventIds` 和 `lastHistoricalEventIds`。合并或压缩必须保留 ID 并集；旧快照缺字段时初始化为空数组，不从正文补造引用。
7. `causal-delay` 的 P1 快照显式使用 `schemaVersion: 1`。带版本快照出现重复事项 ID 时整包拒绝；无版本旧快照的重复 ID 按原顺序确定性重编号，并保留 `legacyId` 作为迁移证据。
