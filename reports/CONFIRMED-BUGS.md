## #1 [HIGH / conf=high] ai-service
**File:** `src/app/api/proxy/route.ts:316`

**Title:** Proxy upstream fetch has no timeout and ignores client abort -> leaked/hung upstream requests, no cancellation

**Detail:** The proxy forwards to the provider with `const upstreamResp = await fetch(apiUrl, { method: 'POST', headers: {...}, body: JSON.stringify(forwardBody) })` (lines 316-322). It never passes a `signal`. The incoming `request.signal` is not read, and no server-side AbortController/timeout is created. Consequences: (1) When the client aborts (user cancels, or the client-side 90s `fetchWithTimeout` fires at ai-client.ts:568), the browser-to-proxy connection is torn down but the proxy keeps its upstream request running to completion — a leaked request that still consumes tokens/quota and cannot be cancelled. (2) If the provider hangs, the proxy has no upstream timeout at all, so the route handler can block indefinitely (only the client's 90s timeout protects the browser; for streaming there is no overall cap once bytes start flowing). Failure scenario: user clicks 'cancel' mid-generation; UI stops, but the DeepSeek call continues for its full duration and bills tokens.

**Trigger:** Verified against the real code. POST(request: Request) at route.ts:235 never references request.signal. The upstream fetch at lines 316-322 passes no `signal`, and the handler creates no AbortController and no setTimeout — there is no server-side cancellation or timeout anywhere in the proxy. No `maxDuration`/runtime/config export exists in the file, so on a self-hosted Node server there is no platform cap either.

Two concrete, reachable failure paths:

(1) Provider hangs: a slow/unresponsive provider that accepts the connection but stalls makes `await fetch(apiUrl, ...)` (line 316) block with no timeout. For non-stream, `await upstreamResp.json()` (line 378) likewise has no cap; for stream, the piped `upstreamResp.body` (line 368) has no overall cap once bytes flow. The route handler can block indefinitely. Trigger: any hung upstream — directly reachable, no guard.

(2) Client abort leaks the upstream call: the ONLY timeout/cancellation in the system is on the browser→proxy hop (ai-client.ts fetchWithTimeout, TIMEOUT_MS=90000 at line 84, merging the caller's signal at 571-573). That signal/timeout is attached to the client's fetch to /api/proxy, not to the proxy's upstream fetch. When the client aborts (user cancel or the 90s timeout), the browser→proxy connection is torn down, but because the proxy's upstream fetch has no signal wired from request.signal, the proxy→provider request continues to completion, still consuming tokens/quota. Trigger: user clicks cancel mid-generation, or the 90s client timeout fires.

Both consequences match the claim exactly and are triggered by ordinary inputs. No upstream guard, not dead code, the fetch is genuinely awaited. The defect is real.

**Fix:** In POST, create `const controller = new AbortController()`; forward client cancellation with `request.signal.addEventListener('abort', () => controller.abort(), { once: true })` (and check `request.signal.aborted` first); add a server cap `const t = setTimeout(() => controller.abort(), N)`; pass `signal: controller.signal` into the upstream `fetch(apiUrl, { ... })` at line 316; for the streaming branch keep the controller alive until the stream ends (clear/abort on stream close) and for the non-stream branch `clearTimeout(t)` in a finally. The existing `.catch(() => null)` already maps an aborted upstream to a 502, so abort handling degrades gracefully.

## #4 [HIGH / conf=high] persistence-migration
**File:** `src/core/store-migration/migration-runner.ts:186`

**Title:** autoMigrateFromDir bumpVersion skips all patch-level migration steps whenever a minor/major bump is pending (migration chain gap)

**Detail:** bumpVersion (lines 135-143) increments the most-significant lagging segment: if major<target.major it jumps straight to {major+1,0,0}; if minor<target.minor it jumps to {minor+1,0}. So migrating current 1.0.0 -> target 1.2.0 produces steps 1.0.0->1.1.0 then 1.1.0->1.2.0 — the patch migrations 1.0.0->1.0.1, 1.0.1->1.0.2, etc. are NEVER attempted, their stepKeys never looked up in MIGRATION_IMPORTERS. Any data-format change shipped as a patch migration file (e.g. 1.0.0-1.0.1.ts) is silently skipped, leaving the stored data in an un-migrated shape while the version key is advanced to 1.2.0, so it will never be retried. Likewise 1.0.5 -> 2.0.0 skips every 1.x.y step.

**Trigger:** Confirmed by reading migration-runner.ts (lines 135-143, 186-228) and its caller. bumpVersion increments the MOST-significant lagging segment, not the least-significant: if major<target.major it returns {major+1,0,0}; else if minor<target.minor it returns {minor+1,0,0}; else patch+1. The while-loop at line 186 builds stepKeys solely from this bump sequence (line 191 stepKey=`${fromVer}-${toVer}`) and only looks those up in MIGRATION_IMPORTERS (line 192).

Concrete reachable path: init-mods-bootstrap.ts line 134 calls autoMigrateFromDir(name, scanEntry.version) with the mod manifest version as target and localStorage `{mod}:version` as current. Stored=1.0.0, manifest=1.2.0, with a shipped patch migration file 1.0.0-1.0.1.ts (codegen scanMigrationFiles regex ^\d+\.\d+\.\d+-\d+\.\d+\.\d+\.ts$ accepts patch-level filenames, stepKey='1.0.0-1.0.1'):
- Iter1: bumpVersion({1,0,0},{1,2,0}) -> minor 0<2 -> {1,1,0}; stepKey looked up = '1.0.0-1.1.0'. The '1.0.0-1.0.1' importer is NEVER queried. No '1.0.0-1.1.0' importer exists -> line 224 silently advances stored version to 1.1.0.
- Iter2: -> {1,2,0}; stepKey '1.1.0-1.2.0'. Loop ends at 1.2.0.
The patch migration 1.0.0-1.0.1 is never executed and the version key is advanced to 1.2.0, so it is never retried (line 171 short-circuits next run). Data left in un-migrated shape. Same for 1.0.5->2.0.0 (jumps straight to 2.0.0, skipping every 1.x.y). This directly violates the module's documented guarantee at line 14 ('版本跳跃自动补全...不会跳过'). No upstream guard prevents patch-named migration files; the function is wired and invoked in production bootstrap. Defect is real and reachable. Currently MIGRATION_IMPORTERS is empty so no live data corruption today, but the latent flaw triggers the moment any patch migration file is added — a high-severity correctness bug in the migration engine itself.

**Fix:** Make the chain walk monotonically by smallest increment, preferring an existing importer. Replace the single bumpVersion call with: first compute the patch-bump candidate {major, minor, patch+1}; if its stepKey has an importer, use it. Otherwise fall back to the segment-bump (current bumpVersion) which advances to the next minor/major boundary as a no-op skip. Concretely, in the loop compute patchNext={...curr, patch:curr.patch+1}, build its stepKey, and if MIGRATION_IMPORTERS[modName]?.[patchStepKey] exists use patchNext; else use bumpVersion(curr,target). This ensures every shipped patch migration (e.g. 1.0.0-1.0.1) is attempted while still leaping over gaps. Add a unit test covering 1.0.0->1.2.0 with a 1.0.0-1.0.1 file present to lock the behavior.
